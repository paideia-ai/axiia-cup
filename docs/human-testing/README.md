# Axiia 真人测试系统

面向产品评审者、真人测试成员和准备测试账号的同学。这里说明如何把规格变成可执行旅程、在产品
Test Mode 中操作、使用正确的测试账号，并留下可追溯的结果。

**核对日期：2026-09-14。** 产品实现以 `axiia-cup` 的 `main@18515a3`
为准；发布版手册已做只读浏览器核对。维护者应使用下文链接的当前源码。文中的数量是此次核对快照，不代表所有条款已经通过人测。

## 1. 第一次参加测试

1. 打开 [v4 总入口](https://deploy-v2-ebon-beta.vercel.app/v4-hub)，进入
   [已审章节真人测试手册](https://deploy-v2-ebon-beta.vercel.app/spec-v4-reviewed-human-test)，选择本次分配的旅程。
2. 在 `axiia-cup-product` 群协调领取对应的**私密账号包**及去敏后的 fixture
   manifest（测试初始状态清单）。按角色卡核对账号、场景、智能体和版本，以及本轮是否需要重新准备。密码由授权的私密渠道交接。
3. 使用账号包中的产品账号登录。确认 Test Mode
   显示的**实际登录邮箱**与账号包相符；昵称只是角色提示。切换相互独立的角色时，可用独立浏览器配置或先退出再登录。
4. 从手册点“打开网页 →”。链接会带 `tm=1`、`tmJourney` 和
   `tmStep`；对于产品已接入的旅程，登录后会回到目标页面并展开指定步骤。也可以直接打开
   [产品测试入口](https://axiia-cup-2-web.isofucius.cn/?tm=1)。
5. 按“做什么 / 应该看到”实际操作。新建智能体或对局后，把本轮真实的
   `/agents/:id`、`/matches/:id` 地址填回所需字段，或在支持的步骤捕获当前页面
   ID。不要沿用上一轮运行时 ID。
6. 在 Test Mode 用自己的实际飞书显示名和**看板口令**记录结果；“不对 /
   跳过”需要说明。再从该步骤的截图链接返回手册，按指定文件名提交证据：**通过和有问题都需要至少一张截图；跳过需要原因**。要点击“发送并记录”，只选状态或只贴图不算提交完成。
7. 确认共享记录提交成功，必要时刷新查看；结束后在手册“导出记录”。再次做会消耗初始状态的
   A3/A6 旅程前，先取得新的已准备账号包，再点该旅程的“开始新一轮”。

**三种东西分别领取、分别使用：**
产品账号密码用于登录产品；测试注册码用于注册步骤；看板口令配合实际执行人姓名用于提交评审/人测结果。产品域名和手册域名的浏览器存储相互隔离，身份不会跨站自动同步。

## 3. 从 spec 到 test journey 的设计

规格以可检查行为为单位：`U##-C##` 是条款 ID，`LACK-nn`
表示规格尚有缺口。规范句说明“在什么状态、发生什么操作、系统必须给出什么响应”；条款版本是判断本次预期的依据。

进入当前人测手册需要同时满足：最新规范句已确认、条款仍有效、无阻断冲突、位于可交接集合。当前完整交接数据有
125 行：107 条最新规范句已确认，其中 104 条可交接；其余包含 3 条暂缓、8
条最新版本待审、10
条归档/合并/缺规格项。**可交接只是允许开始测试，不是已经通过。**

每个步骤必须把以下内容接起来：

| 内容                 | 设计要求                                                          |
| -------------------- | ----------------------------------------------------------------- |
| 稳定的旅程 / 步骤 ID | 调整执行顺序时保留原 ID，已有结果仍能定位                         |
| 条款与 `versionPins` | 精确列出本步验证的条款版本；旧 pin、缺 pin 或损坏记录不算当前完成 |
| 账号角色与初始状态   | 指明所有者/访客、甲乙侧、保存版本与 ★ 参赛标记、门槛、配额等      |
| 页面与业务 ID        | 稳定值可预填；运行时值由本轮产生；需要刷新状态的值不能冒充已就绪  |
| 操作与可见预期       | 写到人能执行并判断；必要时列出 API 回读或组织方协作步骤           |
| 截图与已知限制       | 给准确文件名，区分缺能力、缺测试数据、缺协作窗口、待裁决          |
| 部件映射             | 产品组件的 `data-tm` 标记连接条款和旅程；不能仅凭标记存在判通过   |

例如，A6 的“首次保存自动成为参赛版本”需要一个**没有任何保存版本和 ★
的全新空壳智能体**；已经保存过的账号，即使页面看起来相似，也不能验证首次保存。准备工具提供初始条件，真人仍要亲自完成保存并留下结果。

UIUX 仓库保存规范句、版本确认和交接源数据；产品仓库保存交接快照及 UI
标记映射；共享看板保存实际提交的判断与证据；Git/CI
提供工程验证。更新规格或手册后需要同步产品快照，不能只改页面文案。

## 4. Test Mode 的使用与结果含义

- **开启 / 关闭：** URL 加 `?tm=1`（已有查询参数时用
  `&tm=1`）；浏览器记住开关。`?tm=0` 或右下角 ✕
  关闭。参数处理后可能从地址栏移除，这是正常行为。
- **标记：** 在“全部 → 只显示有条款的 →
  隐藏”之间切换。点部件徽标可看条款、规格锚和旅程；灰色“未映射”和清单“无部件对应”提示映射缺口，尚不能直接认定产品不合格。
- **清单：** 查看本页规格、关联旅程和部件。共享部件在其他页面出现时仍可能保留
  `E.` 或 `OS.` 前缀。
- **导测：** 当前交接优先，历史两轮保留。根据目标页、角色和 fixture
  状态操作；聚光只帮助定位，不会代替点击、生成测试数据或验证实际账号权限。
- **身份：** 使用实际执行人的飞书显示名，不能用 fixture 昵称代替署名。看板身份的
  `core/tester` 标签不会赋予产品管理员权限。
- **截图：**
  产品导测展示准确文件名及手册深链；产品结果按钮本身不上传截图。需要在手册完成证据提交。
- **开始新一轮：**
  清除当前旅程的本机进度和运行时/需刷新字段，再从第一步开始。保留稳定预填值；不重置服务器账号、不删除共享结果。A3/A6
  等初始状态会被消耗的旅程需要先重新准备账号；普通角色切换不需要重开一轮。

不同入口的共享记录按命名空间区分：

| 记录              | 写入内容                                                                                |
| ----------------- | --------------------------------------------------------------------------------------- |
| `ss:<clause-id>`  | 产品导测每确认一步，向本步各条款分别记录 pass/fail/skip；固定版本条款带 `clauseVersion` |
| `pjg:<step-id>`   | 产品导测的步骤结果；固定版本步骤带完整 `versionPins`                                    |
| `sv4hj:<step-id>` | 当前完整手册的步骤结果及截图/评论，按当前版本 pin 判断是否有效                          |
| `pj:` / `pjr2:`   | 历史两轮手册记录                                                                        |
| `sv4r:`           | 规范句/折叠内容的版本审核与讨论，不是人测结果                                           |

导测写入还带前端 build
SHA、执行人角色、步骤和时间；备注附在主要条款下。手册和导测使用不同记录空间，不能把其中一次点击当作两个入口都已交齐证据。

本机导测进度会按当前 pin 过滤，但并未按产品账号、执行人和 build
完全隔离，也不会自动从其他设备恢复。它只是操作便利；共享证据与本次环境仍需核对。网络失败可能发生在多条写入的中途，提交不是跨所有条款的一次原子事务；报错后应检查已落下的记录并重试，不能只凭本机勾选判断提交成功。

本地构建若缺 `VITE_TM_BOARD_URL` 或 `VITE_TM_BOARD_ANON_KEY`，Test Mode
可浏览但不能提交，按钮会报“看板未配置”。维护者应按现有环境配置提供值。

## 5. 测试账号与 fixture

账号包提供的是**满足特定初始状态的角色**，不是可任意互换的通用登录。B3/A5
原始包有六个角色别名：B3 完整所有者、B3 访客缺侧、A5 完整发起方、A5 缺侧玩家、A5
锁定热座、A5 配额被约方。当前 A3/A6
另有独立准备流程，不能拿同一个旧账号覆盖所有步骤。

执行前核对：产品环境、实际邮箱、场景、智能体归属与甲乙侧、保存版本/★、门槛、配额日期，以及
manifest 的 `state`、验证结果和有效期。昵称、历史截图、发布时预填 ID
都不能证明现在仍满足初始条件。

| 账号准备命令（在当前 `v2/web` 执行）       | 准备什么                                                                                | 是否运行真实对局   |
| ------------------------------------------ | --------------------------------------------------------------------------------------- | ------------------ |
| `deno task prepare:human:a3 --apply`       | 一次性注册码与拟用登录信息；**保留未注册状态**给真人测注册/自动登录                     | 否                 |
| `deno task prepare:human:a6 --apply`       | 新的三角色包：双场景门槛玩家、只保存一侧的创建玩家、PvP 未解锁被约方                    | 否                 |
| `deno task prepare:human:a6-entry --apply` | 两个独立新账号：参赛版本切换矩阵；首次保存用空壳智能体                                  | 否                 |
| `deno task prepare:human:a5 --apply`       | 消耗**现有专用 A5 被约方**的 PvP 配额，并验证 `pvp_daily_limit`；保留另一方后续挑战余量 | 是，有显式对局预算 |
| `deno task prepare:human:a6-quota --apply` | 新建专用总配额耗尽账号，用 Hotseat 达到总量 N/N、PvP 使用为 0，并验证 `daily_limit`     | 是，有显式对局预算 |

这些是准备人员的操作入口。精确环境变量、预算、超时、恢复步骤与 manifest 条件见
[HUMAN_FIXTURES.md（本次核对版本）](https://github.com/paideia-ai/axiia-cup/blob/18515a3aa459547a55af905cf06f6d2b5f4563d3/v2/web/e2e/HUMAN_FIXTURES.md)。本次文档核对没有执行准备命令或消耗共享账号配额。

准备与交接规则：

- A3 和原三角色 A6 准备需要管理员环境凭据。当前 A6 entry / quota
  新建模式可以二选一：完整管理员凭据，或明确授权、未被预留的
  `AXIIA_A6_REGISTRATION_CODE`；两者不能混用。entry 需要两次可用注册次数，quota
  需要一次；不能消耗 A3 专门保留的一次性码。
- `AXIIA_PRIVATE_OUT` 存凭据/恢复日志，`AXIIA_PUBLIC_OUT` 存去敏 ID
  与验证证据；按工具要求使用仓库外的新绝对路径。群消息与文档只分享去敏清单，凭据单独交接。
- 只有工具要求的 `ready` 且验证齐全的 manifest 可交接。`partial`
  可能已经创建账号或发出对局，应先检查日志和实际状态，不能盲目重跑。
- A6 entry 的 S01/S02 要两个独立角色；S02
  保存后初始状态即被消耗。重新准备创建新账号，不复原共享账号。
- A5 PvP 耗尽与 A6 总配额耗尽是不同拒绝路径。A6 S06 走“出战 → 左右手互搏 →
  自打一场”，核对自己的 B 侧 ★ 后观察实际 N/N 提示及没有新增对局。
- 配额包按 **UTC+8 零点（16:00 UTC）**失效，后续使用也可能提前破坏状态。A6 quota
  的 `--resume` 使用原私密 checkpoint 和新的输出路径；同账号只运行一个准备进程。
- 原始 `provision-b3-a5-human.ts`
  是有日期限制的初次准备脚本，不是日常重置入口；`seed-dev` 是开发/E2E
  数据工具。当前检查未发现统一的自助账号领取池或一键服务器重置功能。

## 6. 如何记录问题，哪些情况先不要判通过

建议问题记录包含：步骤 ID、条款及版本、前端 build/测试时间、角色别名与去敏业务
ID、操作、预期、实际结果、截图，以及所缺的前置条件。不要在截图、备注或群消息中放密码、注册码、Cookie、Authorization
或 token。

| 情况                                         | 正确处理                                     |
| -------------------------------------------- | -------------------------------------------- |
| 观察到功能不符合该版本要求                   | 记录“有问题”，说明差异并附截图               |
| 缺初始账号状态、缺实时对局、缺组织方协作窗口 | 写清缺什么，保留未完成或按手册跳过；不判通过 |
| 规格冲突/待裁决                              | 保留阻断原因，不能自行选一条解释后判通过     |
| CI 通过、准备工具 `ready`、旧版本已有结果    | 作为工程/初始状态证据；继续做本轮真人步骤    |
| 截图显示暂存本机、提交报错                   | 先补发并确认共享记录，不能当作已交证据       |

当前容易误测的几个例子：

- **A3 首战：**
  保存首个合格版本后还需点“开始首战”；不能沿用“保存自动开打”的旧解释。后续步骤要使用这一次产生的真实对局。
- **B3 当前 NPC：** 从场景的 NPC 入口查看实际 NPC 信息；不能猜 NPC
  ID。当前入口和元数据不等于已满足 U10-C14 的完整双侧统计要求。
- **A6 参赛报名 S04：** 玩家检查/补齐双侧
  ★，组织方通过自身授权会话操作报名并回读参赛名单。没有玩家自助报名按钮本身不构成该条款失败；仍需真实初始数据和组织方协作窗口。
- **A6 同对手挑战次数 S05：**
  当前手册仍标明准备受配额条件阻断；多名发起者填满一个人的累计计数不能证明同对手规则。按当前手册处理，先不宣称完成。
- **版本切换与 Hotseat：** 共享账号已有新版本不应被重置成旧种子；记录当前版本与
  ★。Hotseat 按手册 S01 → S03 → S02 的顺序观察，先看进行中，再等待同一对局结束。

变更旅程时先更新并提交 UIUX 源数据，再同步产品快照；保留 clause pin、源
commit/内容
hash、历史审计日期的原意。不要用新部署时间替代旧审核时间，也不要把工程验证写成真人通过。A3/A4/A6

```sh
deno install --frozen
deno task tm:check
deno task test:human-fixtures
```

`tm:check` 检查标记、条款、步骤、深链、fixture
与版本记录契约；`test:human-fixtures`
离线检查账号准备流程，不联网创建账号。交互改动补跑相应 Storybook/MSW
浏览器测试；真实服务 E2E 使用 `test:e2e:real` 的隔离服务，不能把指向共享 beta
的开发代理冒充隔离环境。
