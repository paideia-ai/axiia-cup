# 十一人陪审团法律场景开发计划（草案）

> **归档说明：** 本文记录方案形成过程，其中的“建议”“待决定”和调用次数已经被正式设计取代。完整权威规格见 [`02-harbor-murder-jury.md`](../../problems/legal-scenarios/02-harbor-murder-jury.md)。不要直接按本草案实现。

## 1. 场景的一句话定义

两名分别主张“证据足以定罪”和“仍有合理怀疑”的玩家陪审员，在五轮公开审议中争取另外九名 NPC 陪审员；双方可以在关键时点发起秘密投票、私下说服、证据复核或提前表决，最后由十一人简单多数票直接决定胜负。

这个场景借鉴《十二怒汉》的核心体验——不同背景的人围绕同一组证据互相影响——但不复制影片的案件、人物、台词或必须全体一致的终局规则。

## 2. 已经确定的设计

1. 场内共有十一名陪审员，不另设一个负责决定胜负的单一 Judge。
2. 两名玩家都是陪审员，不是控辩律师。
3. 玩家甲的初始任务是说服陪审团认定证据足以定罪；玩家乙的初始任务是说服陪审团认定仍有合理怀疑。
4. 另外九名陪审员由不同 persona 的 Agent 扮演；他们不是九个隐藏权重，也不应被预设为永不改变的票。
5. 案件事实、证据、证词和适用的证明标准对所有人公开。
6. 开局不进行也不公布初始投票。
7. 公开审议共五轮。每轮两名玩家都必须发言，其他陪审员有机会选择发言或保持沉默。
8. 五轮结束后必定进行最终判决投票；若提前终局动议通过，则立即进行。
9. 最终裁决采用简单多数：十一票中六票即获胜，不存在平票或悬而未决的结果。
10. 一对一私聊是必备行动。每名玩家最多选择一名 NPC 陪审员，进行三个完整往返，共六次私下发言。
11. 私聊是否发生、对象和内容不向其他游戏角色公开。
12. tool call 的种类不预先限制为三个，但正式首版只保留具有明确取舍和可验证后果的行动。
13. 正式案件使用 8 项编号证据。
14. 每一轮都询问九名 NPC 一次，由每个人决定申请发言或保持沉默；接受这种设计带来的额外模型调用。每轮最多选择三名 NPC 实际公开发言。

## 3. 推荐的世界观和案件方向

### 推荐默认值：现代虚构法域中的原创“码头疑云”

保留现有 `02-harbor-murder-jury.md` 的最小雏形：港口仓库发生命案，被告在现场附近出现，另有第三人进入的可能，陪审团需要判断控方是否排除合理怀疑。

正式版本应重新编写案件，而不是直接沿用当前文件中的隐藏权重、planted truth 和 Weighted Argumentation Framework。推荐理由：

- 门禁、监控、手机连接和法医时间窗等证据自然属于现代案件；
- 玩家容易在短时间内理解“有罪”与“合理怀疑”两种任务；
- 九名陪审员可以分别关注时间线、证人可信度、物证污染、动机、程序公平等不同争点；
- 胜负由真实的十一人投票产生，不需要玩家猜底层权重。

多数裁决可以写成这个虚构法域的公开规则。古希腊、古罗马或法国革命时期的多数陪审制度可以作为制度灵感，但没有必要为了历史出处把现代证据体系全部改写成古代背景。

### 暂不推荐

- 直接复刻《十二怒汉》的弑父案件：版权与创作空间都不理想，也容易让熟悉电影的模型按剧情表演。
- 继承某部现成推理小说的完整谜底：虽然一致性成本低，但会引入版权、模型记忆泄题和“谁读过原作谁占优”的问题。
- 保留隐藏证据权重作为真正裁判：这会重新变成猜 verifier 的数学题，与当前方向相反。

## 4. 案件写作与一致性工程

案件内容在写成玩家材料之前，先建立一个不直接投放给玩家的“案件圣经”。它用于保证创作一致性，不用于秘密评分。

案件圣经至少包含：

1. 分钟级真实时间线；
2. 场所平面图、入口和人物移动路线；
3. 每件证据的来源、采集时间、能证明什么、不能证明什么；
4. 每名证人的实际观察位置、观察条件、记忆误差和表述范围；
5. 控方最强的完整叙事；
6. 辩方至少一条足够具体、但不要求证明真正凶手的合理怀疑路径；
7. 每条材料之间的依赖关系和潜在冲突；
8. 法律指示：无罪推定、举证责任和“排除合理怀疑”的场景内定义。

玩家案件包固定为 8 项编号证据。格式参考《12 Angry AI Agents》附录 B 的“场景环境—案件摘要—编号证据”层次，但每项证据应同时接受定罪方向和合理怀疑方向的检验：

```text
id
name
category
source
public_description
supports_guilt_interpretation
reasonable_doubt_interpretation
limits_and_non_conclusions
related_evidence_ids
```

8 项证据不是 8 个孤立的一句话事实。证词、物证、时间信息和环境条件可以互相组合，但所有依赖关系都必须在案件圣经里写清楚。

这里要区分两种“矛盾”：

- 世界事实自相矛盾，是写作错误，必须消除；
- 两名证人的说法不一致，可以是有意设计的争点，但案件圣经必须解释这种差异为何可能发生。

完成初稿后做四次审计：

- 时间线审计：所有事件在时间和路程上能够发生；
- 证据来源审计：没有无来源、用途漂移或突然改变含义的证据；
- 双方叙事审计：控方和辩方都能形成连贯论证，不是一方天然无话可说；
- 泄题审计：任何单一证据都不能机械地直接给出答案。

作者可以保留一个用于检查一致性的真实事件版本，但脚本不得根据这个秘密版本判胜。最终票数才是胜负依据。

## 5. 十一名陪审员的结构

### 两名玩家陪审员

- **定罪立场陪审员**：认为证据整体已经达到定罪标准，负责建立完整因果链并回应合理怀疑。
- **合理怀疑立场陪审员**：认为控方尚未完成证明责任，负责指出断点并提出可信的替代解释。

两人的比赛目标与最终投票方向固定并公开。这样玩家能够理解自己在争什么，也避免比赛 Agent 在最后突然放弃己方目标。

### 九名 NPC 陪审员

每份 persona 都应包含以下字段：

- 身份背景和与案件无直接利害关系的个人经历；
- 最重视的证据类型；
- 最容易忽略或误读的部分；
- 对多数压力、权威、冲突和情绪表达的反应；
- 发言风格与发言积极度；
- 当前论证中什么问题最可能使其重新思考；
- 哪类充分论证能够使其改变意见；
- 不得虚构证据、不得擅自宣布终局、不得把 persona 写成固定投票结果。

九人应覆盖不同的思考路径，而不是把《十二怒汉》的九个人改名。可以考虑：时间线核对者、证人可信度观察者、物证与污染敏感者、证明标准严格者、重视常识叙事者、容易从众者、反感傲慢表达者、程序公平关注者、善于整合争点的陪审团主席。

首轮 benchmark 先让九人使用同一种模型、不同 persona，以确认人物提示词本身有效；之后再尝试不同模型。否则无法分辨表现差异来自模型还是人物。

## 6. 五轮公开审议

### 每轮骨架

1. 第一名玩家可以选择是否使用一个当下可用的行动，然后公开发言。
2. 第二名玩家可以选择是否使用一个当下可用的行动，然后公开发言。
3. 进入 NPC 自由回应阶段。
4. 记录本轮已经公开的论点、使用过的行动和各 NPC 的内部审议状态。

玩家发言顺序建议交替：

- 第 1、3、5 轮：定罪方先发言；
- 第 2、4 轮：合理怀疑方先发言。

这样不会让一方持续拥有首因或最后回应优势。正式 benchmark 仍应把双方身份和先后顺序对调运行。

### NPC 如何“自行决定是否发言”

采用真实自愿发言：每轮用一次很短的结构化选择询问全部九名 NPC，是保持沉默，还是申请发言。五轮中每人都会获得五次根据最新讨论作出选择的机会。

建议意愿选择至少返回：

```text
decision: PASS | SPEAK_NORMAL | SPEAK_URGENT
reason: 一句内部理由
```

仅选择非 `PASS` 的陪审员进入候选池。若申请者超过本轮公开席位，按照紧迫度、上一轮是否发言、累计发言次数和轮换座次进行确定性选择，避免再引入一个 LLM selector。

- 优点：最接近自由讨论，所有人每轮都能根据最新内容决定。
- 缺点：仅“是否发言”就在五轮产生 45 次模型调用，之后还要生成实际发言。

首版先接受这个成本，并固定为每轮最多三名 NPC 发言：

1. 没有人申请，则本轮没有 NPC 发言；
2. 一至三人申请，则所有申请者发言；
3. 四人以上申请，则只选择排序最靠前的三人；
4. 排序依次比较：`SPEAK_URGENT` 优先、上一轮没有发言者优先、累计公开发言次数较少者优先、当轮轮换座次靠前者优先；
5. 当轮轮换座次的起点依次为第 1、3、5、7、9 个 NPC，避免固定低编号长期占优；
6. 三名入选者按照同一排序依次发言，后发言者可以听见本轮前面 NPC 的公开发言。

`SPEAK_URGENT` 只用于需要立即纠正具体证据错误、回应直接点名，或者回应如果拖到下一轮就会失去上下文的问题。普通补充使用 `SPEAK_NORMAL`，没有新增贡献时使用 `PASS`。NPC 不是竞争玩家，因此允许它们自行报告紧迫度；benchmark 仍要检查是否有人无差别地把每次申请都标成紧急。

### V2 落地方式

每轮先完成全部九人的意愿判断，再开始任何 NPC 公开发言，保证九人的选择基于同一份公开上下文：

```js
const requests = []
for (const juror of jurors) {
  const reply = await juror.agent.act({
    prompt: speakingDecisionPrompt(round),
    fields: {
      decision: { enum: ['PASS', 'SPEAK_NORMAL', 'SPEAK_URGENT'] },
      reason: { hint: '仅供你自己和脚本理解的一句理由' },
    },
  })
  requests.push({ juror, decision: reply.fields.decision })
}

const selected = selectSpeakers(requests, round, speechHistory).slice(0, 3)
for (const juror of selected) {
  juror.agent.push('你的发言申请获选。回应当前讨论，不要提及内部申请流程。')
  const speech = (await juror.agent.say({ channel: 'public' })).text
  deliverPublicSpeechToEveryone(juror, speech)
}
```

意愿判断的 `act` 不设置 `channel`，因此不会形成公开时间线发言；也不设置 `key`，避免把内部理由保存成玩家可见的中间 verdict。公开发言仍使用 `say({ channel: 'public' })`，并由脚本通过 `hear` 明确送给其余十名陪审员。

V2 的 effect/replay 模型会把这些生成调用按确定顺序逐步完成。即使把九个 `act` 写进 `Promise.all`，也不能把它当成九个真实并发的 provider 请求。因此首版直接使用容易理解的顺序循环，并把 45 次意愿判断造成的延迟和输入 token 成本列入 benchmark。

## 7. 行动设计

### 首版核心行动

| 行动 | 建议次数 | 谁知道 | 直接后果 | 主要取舍 |
|---|---:|---|---|---|
| 秘密意向投票 | 每方 1 次起步 | 发起者只看到总票数；其他角色不知道票型和个人选择 | 九名 NPC 给出当前有罪/无罪倾向，连同两名玩家的固定立场汇总为十一票 | 获得局势信息，但使用时点太早可能浪费；次数越多成本越高 |
| 一对一私聊 | 每方 1 次 | 仅发起者和目标 NPC 知道 | 与一名 NPC 进行三个完整往返，目标将交谈纳入自己的后续判断 | 深度说服一个人，放弃影响更多人的公开时间和对象选择机会 |
| 提前终局动议 | 每方 1 次 | 全场知道动议与程序票 | 十一人对“是否现在结束审议”记名表决；达到 8 票即立刻进入最终判决 | 领先时可以锁定结果，误判局势则会暴露急切并消耗机会 |
| 证词重读 | 每方 1 次，和其他证据行动共享额度 | 全场 | 重新展示一段已经公开的证词，并要求相关 NPC 在后续回应中处理它 | 强化共同注意力，但不增加新事实 |
| 物证检查或演示 | 与证词重读共享额度 | 全场 | 把一件已公开物证的尺寸、位置或检测结果以标准化材料重新呈现 | 可以让抽象争论具体化，但不能产生隐藏检测结果 |
| 时间线重建 | 与证词重读共享额度 | 全场 | 按时间排序已公开事实，显式标出空档和冲突主张 | 帮助时间线论证，也可能让对手同样受益 |

“证词重读、物证检查、时间线重建”建议合并成一个每方一次的“证据复核额度”，玩家自行选择复核方式。这样工具种类可以丰富，但不会变成无成本重复按钮。

### 可选行动，先进入 benchmark，不承诺进入首版

| 行动 | 可能价值 | 风险 |
|---|---|---|
| 邀请一名陪审员公开说明 | 让玩家把公开压力放到关键人物身上 | 容易成为无脑点名最摇摆者；需要限制次数 |
| 请求一次记名意向投票 | 获得每个人的公开立场，制造社会压力 | 会显著削弱秘密投票和秘密私聊的价值 |
| 请陪审团主席归纳当前争点 | 让长对话重新聚焦 | 主席模型可能凭总结获得过强议程设置权 |
| 请求澄清法医报告 | 有利于围绕专业证据讨论 | 如果回答包含原材料没有的事实，就违反“证据完全公开” |
| 短暂休会 | 让某些 NPC 降低情绪或重新阅读材料 | 状态变化难以向玩家解释，容易退化成隐藏数值 |
| 放弃本轮公开发言以换取第二次私聊 | 形成明显资源取舍 | 会打破“两名玩家每轮必定发言”的已定规则，只适合作为远期变体 |

### 私聊的具体协议

1. 每名玩家整局最多使用一次，只能选择九名 NPC 之一；双方可以不知情地选择同一目标。
2. 行动在玩家自己的公开发言时段触发，叙事上是两人短暂离席到走廊、取水处或洗手间附近交谈。
3. 三个完整往返的顺序为：玩家发言、NPC 回应，重复三次，共六次发言。
4. 私聊结束后玩家回到审议室，继续完成该轮公开发言；私聊不额外占用一个公开轮次。
5. 系统不向其他角色发送“有人私聊”的事件，不把对象或文本写入他们的上下文。
6. 私聊提示要求双方不得在公开阶段复述私聊内容或点名私聊对象；NPC 可以吸收论证并改变观点，但不能公开说明信息来源。
7. 在实现前必须检查 V2 的 live feed、持久化数据和观众页面是否会暴露私聊频道。至少要保证对手 Agent 和其他 NPC 收不到这些内容；观众实时可见性与赛后回放可见性另行决定。

## 8. 投票与胜负

### 秘密意向投票

- 它是局势侦察，不触发终局。
- 两名玩家各计入一张与己方立场一致的票；九名 NPC 独立提交当前选择。
- 发起者只看到“有罪 X 票、无罪 Y 票”，不知道每名 NPC 的选择。
- 不向其他游戏角色公布有人发起、何时发起或结果是什么。
- “每方一次”是首版推荐值；“每方三次”保留为高成本实验，因为每次都要取得九个独立判断。

### 提前终局动议

- 这是公开的程序表决，不是最终有罪/无罪表决。
- 建议门槛为 8/11，即严格超过三分之二。
- 若通过，立即进行最终判决；若失败，审议继续且该方不能再次发起。
- 不建议采用 6/11：简单多数阵营可能在刚领先时立刻终止游戏，削弱后续说服。

### 最终判决

- 两名玩家分别投己方主张的一票。
- 九名 NPC 独立输出结构化结果：`verdict`、最关键证据编号、简短理由。
- 有罪达到 6 票，定罪立场玩家获胜；否则合理怀疑立场玩家获胜。
- 自然语言中的“大家已经同意”没有程序效力；只有脚本收集的结构化投票能够结束比赛。
- 不再使用隐藏证据权重、最优论证图或另一个 LLM Judge 推翻陪审团票数。

## 9. V2 实现拆分

正式实现应放到 V2 的 canonical scenario 目录，而不是继续把本 scratchpad 当作运行时权威。建议拆成以下模块：

1. 公开案件材料与证据卡；
2. 两名玩家的角色和立场提示词；
3. 九名 NPC persona 与独立 session；
4. 五轮公开发言调度；
5. 行动的可用次数、时机和状态机；
6. 私聊信息路由与可见性；
7. 秘密意向投票、提前终局程序票和最终判决票；
8. 票数统计和唯一终局；
9. 可复现的运行日志、行动日志和逐陪审员投票轨迹。

这里的 tool call 应实现为场景脚本预先定义的 `affordance`，不是让 Agent 访问外部系统的通用工具。

## 10. 验证与 benchmark

### 静态与确定性测试

- 十一名席位和角色名唯一；
- 五轮结束一定进入最终投票；
- 6/11 的胜负边界正确；
- 提前终局门槛和失败后继续流程正确；
- 每种行动的次数不会被重复消耗或绕过；
- 私聊恰好三个完整往返；
- 对手和非目标 NPC 的 prompt 中不存在私聊事件、对象或内容；
- 不合法的证据编号、投票标签或行动参数会被拒绝；
- Agent 自称形成共识不会改变脚本状态。

### 真实模型 benchmark

每个实验条件至少重复多次，并同时镜像双方身份和首轮发言顺序：

1. 九名 NPC 同模型、不同 persona；
2. 九名 NPC 使用不同模型；
3. 交换模型与 persona 的对应关系；
4. 有无明确的“遇到有力论证时更新观点”要求；
5. 最多三人规则下的申请率、入选率、连续发言率和各席位发言次数；
6. 有无秘密意向投票；
7. 有无一对一私聊；
8. 双方 prompt 对调、发言顺序对调。

至少记录：

- 最终票数和每名 NPC 的最终理由；
- 每次意向投票到最终投票的变化；
- 首因效应、模型偏置和角色偏置；
- 是否回应过对方的具体论点；
- 私聊对象、时机及其后续投票变化，仅用于赛后评估；
- tool call 使用率、时机和是否真正改变局势；
- 虚构证据、虚构共识、非法终局和格式错误；
- 模型调用数、token、成本、延迟和失败率。

相关研究笔记见 [`12-angry-ai-agents-paper-notes.md`](./12-angry-ai-agents-paper-notes.md)。论文的关键警告是：多 Agent 持续发言不等于真正互相说服，因此 benchmark 必须观察观点变化和具体回应，不能只看最终文本是否热闹。

## 11. 分阶段交付

### 阶段 A：冻结案件骨架

- 确定案件名称、被告、被害人、地点和法律问题；
- 从当前“码头疑云”中选择可用元素，并重写为 8 项相互关联的编号证据；
- 完成案件圣经和双方叙事；
- 通过四项一致性审计。

阶段 A 的 v0 已形成：

- 公开材料：[`harbor-murder-public-case-v0.md`](./harbor-murder-public-case-v0.md)
- 作者用案件圣经：[`harbor-murder-case-bible-v0.md`](./harbor-murder-case-bible-v0.md)

### 阶段 B：冻结人物与规则

- 写完两名玩家角色和九名 NPC persona；
- 冻结五轮发言规则；
- 冻结首版行动、次数和触发时点；
- 冻结意向投票、提前终局和最终判决协议。

### 阶段 C：V2 原型

- 先用统一模型和最小 UI 能力跑通十一人会话；
- 实现公开/私聊信息边界；
- 实现核心行动和三类投票；
- 保存足以复盘每名陪审员变化的 artifact。

### 阶段 D：低成本验证

- 使用确定性 fake model 覆盖状态机和边界；
- 用少量真实模型检查 prompt、发言长度、工具选择和信息泄漏；
- 估算一整局的调用数、成本与时长。

### 阶段 E：平衡 benchmark

- 运行镜像和多次重复实验；
- 检查是否存在稳定的先手优势、立场优势或某个 NPC 的决定性偏置；
- 比较工具开关与发言调度方案；
- 根据证据调整 persona 和程序规则，而不是暗改隐藏权重。

### 阶段 F：正式内容与呈现

- 冻结玩家可见材料和 scenario prompt；
- 决定观众何时可以看到私聊和秘密投票；
- 设计十一席位、当前公开阶段、已使用行动和最终票型的前端呈现；
- 最后再进入部署和生产验证。

## 12. 写代码前仍需决定的事项

这些问题不妨碍继续写案件和人物，但会影响运行时实现：

1. 场景是否继续使用“码头疑云”名称，以及现有 14 条证据中的哪些元素进入重写后的 8 项证据；
2. 秘密意向投票首版是每方一次、每方三次，还是双方共享三次；
3. 提前终局是否采用推荐的 8/11；
4. “证据复核额度”是否进入首版，以及它是否占用玩家当轮公开发言；
5. 私聊只对游戏角色保密，还是连实时观众也必须不可见；赛后回放是否公开；
6. 九名 NPC 首版是否先统一模型，确认 persona 后再引入多模型；
7. 玩家是否能在最终票前明确做一段极短的总结，还是第五轮发言已经视为结案陈词。

在这些问题中，最先需要解决的是 8 项证据的案件骨架。NPC 每轮全部接受询问、每轮最多三人发言以及超过三人时的选择规则都已经确定。
