# 游戏："泄露之后"：数据泄露集体诉讼认证双人游戏

> 建议部署场景 ID：`legal-data-breach-class`
> 建议部署标题：`泄露之后`
> 建议部署参数：10 轮认证听证；每次发言不超过 3 句话；赛后提交认证要件判断。
> 建议隐藏层：类成员异质性、共同问题权重和损害模型可行性隐藏；双方各有 3 个程序请求，随机 1 个为真目标。
> 程序化确定性判决：是，底层为 Weighted Max-CSP。

## 背景

云书 App 发生数据泄露，约 80 万用户的邮箱、手机号、阅读记录和部分支付尾号外泄。原告代表用户申请集体诉讼认证。被告主张用户损害差异巨大：有人只泄露邮箱，有人泄露阅读记录，有人遭遇诈骗，有人没有任何实际损失。

法庭当前只决定是否认证集体诉讼及认证范围，不处理最终责任。

## 角色

| 角色 | 控制方 | 立场 |
|------|--------|------|
| **用户代表律师** | 玩家甲的 LLM | 主张共同问题占优，应认证集体诉讼 |
| **平台律师** | 玩家乙的 LLM | 主张个体问题过多，不应认证或应极度缩小 |
| **程序化认证法官** | 系统 verifier | 根据认证要件和损害模型可行性计算结果 |

## 公开事实

| 编号 | 事实 |
|------|------|
| F1 | 泄露源是同一个对象存储桶权限配置错误。 |
| F2 | 所有受影响用户均泄露邮箱和手机号。 |
| F3 | 约 18% 用户泄露阅读记录。 |
| F4 | 约 2% 用户泄露支付尾号。 |
| F5 | 原告专家提出统一市场价值模型，估算隐私数据损失。 |
| F6 | 被告专家称不同用户阅读记录敏感度差异极大。 |
| F7 | 平台服务条款中有安全承诺，但不同版本条款措辞不同。 |
| F8 | 平台在泄露后统一发送通知，并提供一年身份监测。 |
| F9 | 约 1,200 名用户报告疑似钓鱼诈骗。 |
| F10 | 平台日志显示权限配置错误持续 37 天。 |
| F11 | 拟任代表人许岚泄露邮箱、手机号和阅读记录，未泄露支付尾号。 |
| F12 | 许岚没有与其他用户不同的单独和解协议，也没有与平台的雇佣或亲属关系。 |
| F13 | 许岚的律师团队已代理过两起数据安全集体诉讼，但统一市场价值模型由新聘专家提出。 |
| F14 | 另一名拟任代表人周闻只泄露邮箱和手机号，未报告诈骗损失。 |

## 认证变量

```text
N: 人数众多
C: 存在共同法律或事实问题
T: 代表人典型性
A: 代表充分性
P: 共同问题是否占优
S: 集体诉讼是否优于个别诉讼
D: 损害模型是否可用类范围计算
Sub: 是否应分子类
```

hard constraints：

```text
certification requires N and C and T and A and P and S
D strongly supports P, but P can still pass for liability-only class
Sub is required if sensitive_reading_record users are materially different
```

## 程序请求

### 用户代表律师请求

| 编号 | 请求 |
|------|------|
| UC1 | 认证全体受影响用户的责任问题类。 |
| UC2 | 设立阅读记录泄露用户子类。 |
| UC3 | 采纳统一市场价值损害模型。 |

### 平台律师请求

| 编号 | 请求 |
|------|------|
| DC1 | 拒绝损害赔偿类，只允许个别诉讼。 |
| DC2 | 至多认证通知义务是否违反的单一问题类。 |
| DC3 | 排除原告专家统一市场价值模型。 |

## 游戏流程

### 第一阶段：共同问题，3 轮

双方争论对象存储配置错误、统一安全义务和日志事实是否足以形成共同问题。

### 第二阶段：个体差异，3 轮

双方讨论泄露字段差异、服务条款版本差异和诈骗损害差异。

### 第三阶段：损害模型与子类，4 轮

双方必须提出可执行认证边界：全体类、问题类、子类、拒绝认证或混合方案。

### 第四阶段：结构化提交

```json
{
  "findings": {
    "N": true,
    "C": true,
    "T": true,
    "A": true,
    "P": true,
    "S": true,
    "D": false,
    "Sub": true
  },
  "certification": "deny|liability_class|damages_class|issue_class|subclasses",
  "classDefinition": "不超过 80 字",
  "proceduralRelief": ["UC1", "UC2"],
  "opponentTrueRequestGuess": "DC3",
  "explanation": "不超过 220 字"
}
```

`proceduralRelief` 只能填写本方请求编号，表示本方希望认证法官单独计入的程序性认证边界或专家处理。若该编号与本方真请求一致，且 certification、classDefinition 或损害模型处理能实际承载该请求，则该项得分。

## 程序化认证法官

verifier 计算每个认证要件和认证边界：

| 项目 | 分值 |
|------|------|
| 认证变量赋值正确 | 40 |
| certification 类型符合 hard constraints | 25 |
| classDefinition 覆盖正确人群且不过宽 | 15 |
| 正确处理损害模型与责任问题的分离 | 10 |
| 本方真程序请求被提交方案满足 | 5 |
| 猜中对手真请求 | 5 |

## 胜负规则

双方独立得分。用户代表律师若主张 damages_class 但 D 为 false，会受到重大惩罚；平台律师若完全否认共同问题而 C 明显为 true，也会受到重大惩罚。

## 核心张力

1. 同一个泄露事件支持共同责任问题，但不必然支持统一损害。
2. 子类可能帮助认证，也可能暴露原告方案过宽。
3. 被告若只强调个体损害，可能无法击败责任问题类。
4. 最优答案可能是部分认证，而不是全体认证或完全拒绝。
