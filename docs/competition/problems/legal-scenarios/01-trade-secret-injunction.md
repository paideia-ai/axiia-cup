# 游戏："源代码之门"：商业秘密临时禁令双人游戏

> 建议部署场景 ID：`legal-trade-secret-injunction`
> 建议部署标题：`源代码之门`
> 建议部署参数：10 轮辩论；每次发言不超过 3 句话；赛后各提交 1 份结构化禁令方案。
> 建议隐藏层：没有隐藏事实；每方 3 个救济请求中，运行时随机 1 个为真目标，其余 2 个为诱饵目标。
> 程序化确定性判决：是，底层为 Weighted Max-CSP / Weighted Max-SAT。

## 背景

原告星桥科技开发一套物流调度引擎。前首席架构师林岫离职后加入被告北陆智能。北陆两个月后发布了相似功能，且演示视频中出现了与星桥内部调试界面相近的字段名。

星桥申请临时禁令，要求停止北陆发布新产品、交出相关代码仓库并禁止林岫参与调度模块。北陆主张：相关思路来自公开论文，字段名只是行业惯例，禁令会让其失去融资窗口。

法庭当前只处理临时禁令，不处理最终侵权责任。

## 角色

| 角色 | 控制方 | 立场 |
|------|--------|------|
| **星桥律师** | 玩家甲的 LLM | 证明商业秘密存在、被不当获取和使用，请求临时禁令 |
| **北陆律师** | 玩家乙的 LLM | 否认秘密性与使用关系，主张禁令过宽且损害过重 |
| **程序化衡平法官** | 系统 verifier | 根据隐藏约束计算禁令是否成立及救济是否适配 |

为方便模板描述，下文把星桥律师记为 `roleA`，把北陆律师记为 `roleB`。

## 公开材料包

每局从材料池中抽取 12 条证据，全部公开给双方，但底层权重不公开。

| 编号 | 材料 |
|------|------|
| E1 | 星桥代码仓库中有 `route_shadow_cost` 字段，北陆演示视频中出现同名字段。 |
| E2 | 星桥内部 wiki 标注该字段为临时调试项，未进入客户文档。 |
| E3 | 林岫离职前一周下载过调度模块压缩包。 |
| E4 | 林岫称下载是为了交接，离职后没有保留本地副本。 |
| E5 | 北陆产品使用的核心算法可在三篇公开论文中找到相似思路。 |
| E6 | 北陆提交了一份独立开发时间线，但其中两次提交没有对应代码差异。 |
| E7 | 星桥与林岫签过保密协议，但没有单独列出调度字段清单。 |
| E8 | 星桥给部分试点客户展示过调度界面，但客户协议禁止截图和传播。 |
| E9 | 北陆若被全面禁售，下一轮融资可能失败。 |
| E10 | 星桥已有两名客户暂缓续约，理由是北陆报价和功能相近。 |
| E11 | 第三方审计发现两个系统的异常处理路径高度相似。 |
| E12 | 北陆称异常处理路径来自开源项目，但未能指出具体版本。 |

## 底层变量

程序化实例至少包含以下变量，运行时可扩展到 40 到 120 个变量。

```text
S: 信息是否构成商业秘密
M: 星桥是否采取合理保密措施
A: 林岫是否有接触机会
C: 北陆是否复制或实质使用
P: 公开资料是否足以独立开发
H: 星桥是否存在不可弥补损害
B: 禁令对北陆的损害是否过重
N: 是否需要窄化禁令
```

法律要件作为 hard constraints，证据关系作为 weighted soft constraints。例子：

```text
S requires M
C is supported by E1 + E11 + E12
P attacks C
H is supported by E10
B attacks full_product_ban
N is supported when C is uncertain but A and H are strong
```

## 救济请求

每方有 3 个公开请求，运行时各随机 1 个为真目标。

### 星桥律师请求

| 编号 | 请求 |
|------|------|
| ST1 | 禁止北陆发布调度引擎 60 天，并允许第三方代码审计。 |
| ST2 | 只禁止林岫参与调度模块，允许北陆继续销售非调度功能。 |
| ST3 | 要求北陆封存离职后两个月内的所有相关代码提交记录。 |

### 北陆律师请求

| 编号 | 请求 |
|------|------|
| BL1 | 若有禁令，只能限于 `route_shadow_cost` 相关字段，不得禁止整套产品。 |
| BL2 | 要求星桥提交保证金，覆盖北陆被错误禁令造成的融资损失。 |
| BL3 | 排除星桥客户流失证据，理由是客户邮件含有未经核实的市场传闻。 |

## 游戏流程

### 第一阶段：禁令听证，10 轮

双方围绕四个禁令要件展开：

1. 商业秘密是否存在；
2. 是否有不当获取或使用；
3. 是否存在不可弥补损害；
4. 衡平救济应宽还是窄。

双方必须同时完成三件事：

- 为己方大立场争取程序化判决；
- 推动自己的真请求被 verifier 认为合理；
- 避免诱饵请求被对方利用，或被 verifier 判为过度主张。

### 第二阶段：结构化提交

双方各自提交 JSON：

```json
{
  "findings": {
    "S": true,
    "M": true,
    "A": true,
    "C": true,
    "P": false,
    "H": true,
    "B": false,
    "N": true
  },
  "remedy": ["ST2", "ST3"],
  "opponentTrueRequestGuess": "BL1",
  "explanation": "不超过 220 字"
}
```

## 程序化判决器

verifier 不根据语言风格打分，而是将提交与隐藏约束实例比较：

| 项目 | 分值 |
|------|------|
| 事实变量与最优赋值一致 | 45 |
| 法律 hard constraints 未被违反 | 20 |
| 救济方案与最优窄化程度匹配 | 15 |
| 能解释主要冲突证据 | 10 |
| 猜中对手真请求 | 5 |
| 自己诱饵请求未被纳入 remedy | 5 |

若提交违反 hard constraint，例如既称信息不保密又主张全面商业秘密禁令，该项直接归零并触发矛盾惩罚。

## 胜负规则

双方独立得分，得分高者胜。若同分，以 hard constraint 违反次数少者胜；仍同分，以救济方案更窄且覆盖真风险者胜。

## 核心张力

1. 星桥若只追求全面禁令，可能赢得侵权叙事却输在衡平救济过宽。
2. 北陆若只说公开资料足够，必须解释异常处理路径和缺失提交记录。
3. 真请求必须嵌入禁令宽窄争论，不能像额外交易。
4. 程序化判决鼓励全局一致，而不是单点雄辩。
