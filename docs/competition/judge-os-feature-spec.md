> 状态：合入候选 v1 的产品决策已确认并实现；Context 对照实验和一致性验证尚待执行
> 最后更新：2026-07-17
> 权威关系：[DESIGN_SPEC.md](DESIGN_SPEC.md) 是产品决策的唯一标准；本文细化 Judge OS 的产品语义、技术行为和实验计划。若两者冲突，以 `DESIGN_SPEC.md` 为准。

## 1. 产品定义：Vibing Judge OS

Judge OS 是辩论期间由裁判角色生成的“即时倾向轨迹”。在商鞅场景中，除最后一组发言外，秦孝公每听完商鞅和甘龙各一次发言，就记录：

1. 此刻更倾向商鞅还是甘龙；
2. 当前这组发言中，什么内容造成了这个倾向。

“Vibing”强调的是产品体验：用户不必等到最终裁决，便能看到每组论辩在秦孝公那里“有没有打中”、倾向如何摆动，以及哪句话可能产生了作用。它可以用于：

- 增强观赛感，让最终结果之前就有可阅读的态度轨迹；
- 帮助玩家调试 prompt，定位具体哪组发言有效或失效；
- 为裁判一致性、模型偏差和说服过程研究提供逐轮数据。

Judge OS 的边界同样重要：

- 它不是最终判决，也不参与最终计分；
- 它不会进入商鞅或甘龙的对话上下文；
- 它不会作为证据传给最终裁判；
- `reason` 是面向用户的简短结构化解释，不是模型的私有 chain-of-thought，也不能被当作裁判真实心理状态的直接观测；
- 单次 `tendency` 是二元选择，不是胜率或概率。

## 2. 已实现的基础版本

当前基础版本仅用于 `shangyang-court`。

| ---------------- | ---------------------------------------------------------------------------------------------------------- |
| 触发时机         | 除最终偶数回合外的第 2、4、6……回合后。10 回合制为 2/4/6/8；20 回合制为 2/4/6……18                           |
| 当前输入         | 只包含刚完成的两次发言；不包含更早辩论、先前 OS 或先前倾向                                                 |
| 裁判模型         | 与场景最终裁判使用同一模型；当前生产商鞅场景为 GLM-5.1，thinking 未被关闭                                  |
| 人设来源         | 独立的 Judge OS prompt，但继承生产秦孝公 judge prompt 的身份、初始立场、政治顾虑和防注入约束               |
| 输出             | 严格 JSON：`afterTurn`、`tendency`、`reason`                                                               |
| 倾向             | 必须二选一：`商鞅` 或 `甘龙`                                                                               |
| 原因             | 每轮必填，不因倾向是否改变而省略                                                                           |
| 对辩论的影响     | 无；Judge OS 在 sidecar 中生成，辩论不等待它                                                               |
| 多轮并发         | 每个已完成的两回合立即启动独立任务，不等待上一条 OS；多条 OS 可以同时生成                                  |
| 乱序处理         | 允许模型乱序返回，但只按第 2、4、6……回合的连续顺序持久化和展示；失败回合先发布不可用占位，后续结果才可展示 |
| 失败策略         | Best-effort；单条生成或中间持久化失败不使对局失败，已完成结果照常保留                                      |
| 恢复             | 已保存的连续成功/失败状态不重复生成；恢复时只补齐缺失的已完成回合组                                        |
| 对最终裁判的影响 | 无数据依赖；最终裁判看不到 Judge OS。辩论结束后立即进入赛后问询和最终裁决，不等待 OS                       |
| 最终收尾         | 计分完成后等待仍在运行的 OS，默认最多 30 秒；超时项标记为不可用，不阻塞或推翻裁决                          |
| 前端布局         | 宽屏时 OS 轨迹框位于辩论框右侧；窄屏自然换行到辩论框下方                                                   |
| 前端时序         | 发言一经 dialogue LLM 返回便立即展示；OS 生成后独立追加，绝不为等待 OS 而暂缓后续发言展示                  |
| 运行溯源         | 每场保存 OS prompt 快照/hash、模型、thinking、temperature、JSON mode、C0 和回合配置                        |

当前“继承生产裁判人设”是两个 prompt 在内容和版本管理上的约束，不是运行时自动拼接。`judgePrompt` 与 `judgeOsPrompt` 是两个独立字段；修改生产 judge prompt 时必须同步审查 Judge OS prompt 是否仍然保持相同的人设、初始立场和防注入规则。管理员界面会提示这一约束；每场运行的 Judge OS provenance 会固定当时实际使用的 OS prompt 快照和 hash、模型及请求配置，避免事后无法还原。

### 2.1 执行时序

```text
商鞅 Turn 1 ─→ 甘龙 Turn 2 ─→ 启动 OS_2 ───────────────────┐
                           辩论继续                         │
商鞅 Turn 3 ─→ 甘龙 Turn 4 ─→ 启动 OS_4 ───────────────┐   │
                           辩论继续                     │   │
商鞅 Turn 5 ─→ 甘龙 Turn 6 ─→ 启动 OS_6 ───────────┐   │   │
                                                   ↓   ↓   ↓
模型可乱序完成，例如 OS_4 → OS_2 → OS_6
                           ↓
按 afterTurn 连续发布 OS_2 → OS_4 → OS_6
                           ↓
最终一组发言完成（不启动 OS）──→ 立即进入赛后问询、最终裁决和计分
                                      ↘ 尚未完成的 OS 继续并行
计分完成 ──→ 最多等待 OS 30 秒 ──→ 保存完整或部分 OS 状态
```

因此，第二条 OS 只需要等待第二组辩论完成，不需要等待第一条 OS 完成。

## 3. 核心设计问题：每轮 Judge OS 应该看到什么 Context

设第 `r` 组辩论为：

```text
D_r = Turn_(2r-1) + Turn_(2r)
O_r = { tendency_r, reason_r }
T_r = tendency_r
```

所有方案都应使用同一份秦孝公人设和相同输出格式；变化的只是每轮 user context。

| 方案                              | 每轮输入                       | 表达的产品语义               | 可保持 OS 之间完全并发 | 优点                                             | 主要风险                                                  |
| --------------------------------- | ------------------------------ | ---------------------------- | ---------------------- | ------------------------------------------------ | --------------------------------------------------------- |
| **C0：当前两回合**（已实现）      | `D_r`                          | 对当前这组发言的即时反应     | 是                     | 因果归因最清楚；成本固定；可独立重放；无自我锚定 | 不记得累计证据；相邻倾向可能跳动；与最终判决不必收敛      |
| **C1：当前两回合 + 全部先前 OS**  | `D_r + O_1...O_(r-1)`          | 带完整自述记忆的连续心理轨迹 | 否                     | 叙事连贯，能引用过去理由                         | 必须等先前 OS；context 递增；错误和措辞会级联；强确认偏差 |
| **C2：当前两回合 + 全部先前倾向** | `D_r + T_1...T_(r-1)`          | 带压缩态度历史的连续轨迹     | 否                     | 比 C1 短；能知道过去站队变化                     | 仍需串行；只有结论没有理由；容易锚定于自己的旧答案        |
| **C3：当前两回合 + 上一轮倾向**   | `D_r + T_(r-1)`                | 一阶状态机式的态度更新       | 否                     | Context 很短；比 C2 更容易控制                   | 仍需串行；对上轮偶然错误敏感；可能人为制造“态度惯性”      |
| **C4：截至当前的全部辩论**        | `D_1...D_r`，不含先前 OS       | 对全部已听证据的累计信念     | 是                     | 更接近最终裁判的信息积累；没有自我反馈；仍可并发 | Context 随回合增长；难判断本轮具体贡献；反复处理旧内容    |
| **C5：最近 K 组辩论**             | `D_(r-K+1)...D_r`，不含先前 OS | 有限记忆的累计信念           | 是                     | 在累计感、成本和并发之间折中                     | K 是新增超参数；窗口外的重要证据会消失                    |

补充说明：完整 `O_r` 已经包含 `tendency`，所以“全部先前 OS + 全部先前 tendency”在数据上是重复的；除非为了固定格式，否则不应把倾向再注入一次。

任何依赖先前 `O` 或 `T` 的方案，都要求上一轮 Judge OS 先完成，因而会取消当前实现的 OS 间并发。若在前一条尚未完成时“先用已有部分历史”继续生成，输入会随网络完成顺序变化，导致不可复现，不建议采用。

### 3.1 v1 决定与 Context 实验优先级

1. **v1 已确定使用 C0。** 它最符合“每组发言有没有打中秦孝公”的即时反应计，也最容易解释和并发执行。
2. **优先把 C4 作为一致性实验的对照。** 它能表达累计信念，同时不读取过去的模型答案，因此不会自我锚定，也不破坏并发。
3. **用 C5 检验 C4 的成本优化。** 若 C4 更一致但上下文成本过高，可以测试最近 2–3 组发言是否足够。
4. **C1/C2/C3 只作为连续性研究，不建议直接成为默认值。** 更平滑的轨迹可能来自自我锚定，而不代表更正确地理解了辩论。

v1 的产品语义已经确定为**当前两回合的即时反应**。以下区分仍适用于后续实验解释：

- 如果 Judge OS 是**即时反应计**，C0 的每轮局部归因比最终一致性更重要；
- 如果 Judge OS 是**累计信念状态**，C4 应当比 C0 更接近最终政策判断；
- 不能仅因为某方案与最终裁决更一致，就断言它更适合“即时反应”产品。

## 4. UI 与用户体验

### 4.1 布局

当前 UI 在宽屏把 Judge OS 作为独立框放在辩论框右侧，窄屏时放到辩论框下方。OS 框使用紧凑倾向轨迹：

- `第 1–2 回合 · 倾向甘龙 → 第 3–4 回合 · 倾向商鞅`；
- 点击成功节点展开该轮 `reason`；
- 失败节点显示“未能生成”，后续节点仍按顺序继续；
- 未完成时显示当前已触发但仍在生成的 OS 数量。

v1 不在 OS 框中额外加入“仅供展示 / 非最终裁决 / 非 chain-of-thought”的短说明文案；这些仍是数据和产品边界，但不作为本版前端提示。Vibing 体验以后可以继续扩展为折线/摆动轨迹。

### 4.2 发言与 OS 的前端展示时序

曾考虑两种方案：

1. **即时发言 + 独立 OS（v1 已选择）**：dialogue LLM 每返回一个发言，前端就立即展示；每个偶数回合触发的 OS 在自身生成完成后再展示。后续辩论不等待 OS。
2. **按 OS 卡住可见发言（未选择）**：先展示 Turn 1–2，等待并展示 OS_2 后，才允许前端展示已经生成的 Turn 3–4；之后依此类推。该方案只限制 UI 展示，不必限制后端辩论生成，但会人为制造观赛停顿。

v1 选择方案 1。OS 可以乱序完成，但前端不得先展示 OS_4 再展示 OS_2；只有 OS_2 成功展示或先出现“未能生成”占位后，OS_4 才能出现。发言本身不受这个顺序缓冲影响。

### 4.3 语义约束

以下约束用于产品解释和测试，不要求以额外说明文案显示在 OS 框中：

- C0 下的相邻节点是对不同发言组的独立反应，不是模型显式记忆后的态度更新；
- 出现 `甘龙 → 商鞅` 只说明两组发言分别触发了不同倾向，不能声称模型知道自己“改变态度”；
- 不展示供应商的隐藏 reasoning；只展示受 schema 约束的 `reason`；
- 即使生成完成顺序不同，用户看到的顺序也必须稳定。

## 5. 与最终裁决的一致性验证

### 5.1 为什么可以复用已有对局

Judge OS 与最终裁判在数据上解耦：它不改变辩论、不改变赛后问询，也不进入最终 judge prompt。因此，只要已有对局保留了完整 transcript，就可以离线逐组生成 Judge OS，不必重新生成玩家对话。

实验时必须避免标签泄漏：最终政策判断只用于事后对比，不能出现在任何 Judge OS 输入中。离线结果应写入独立 benchmark artifact，不应回写成历史生产对局的原生 OS。

### 5.2 模型和 Prompt 对齐要求

“使用同一模型”是最低要求，但仅匹配显示名称还不够。每条实验记录至少要固定并保存：

- 最终裁判使用的 repo model id、provider 和实际 API model；
- thinking/reasoning 模式，包括“显式开启”“显式关闭”或“使用 provider 默认值”；
- temperature、JSON mode 和其他会影响采样的参数；
- 最终 judge prompt 的版本或 hash；
- Judge OS prompt 的版本或 hash，以及它继承的人设快照；
- scenario snapshot、完整 transcript hash 和 prompt-pair hash。

对于某个最终判断，必须用生成该判断的同一 judge model/config 生成 Judge OS。不能用 GLM-5.1 的 OS 去解释 DeepSeek、Claude 或另一个 GLM thinking 配置作出的最终判断。

### 5.3 比较对象

定义：

```text
T_r = 第 r 组后的 Judge OS tendency
F   = 最终政策判断

商鞅 tendency  ↔  变法
甘龙 tendency  ↔  维持现状
```

比较时使用最终 judge JSON 中的政策字段 `judgment`，不要使用整场比赛的 `winner`。比赛胜负还可能受请求达成、问询答案和程序化计分影响，不等于单纯的“变法/维持现状”判断。

单次二元 `T_r` 不是概率。若要比较“每轮倾向概率”和“最终变法概率”，必须在同一实验分组内计算经验比例：

```text
p_os(g, r)    = 分组 g 在第 r 组输出“商鞅”的次数 / 第 r 组有效 OS 样本数
p_final(g)    = 分组 g 最终输出“变法”的次数 / 有效最终判决样本数
```

分组 `g` 至少要固定：场景、prompt pair 或 benchmark condition、judge model/config、judge prompt 版本和 thinking 模式。把不同 prompt pair 的历史对局直接合并，只能得到该混合人群的总体变法率，不能称为某个 prompt pair 的胜率。

### 5.4 推荐指标

| 指标                           | 回答的问题                                                                     |
| ------------------------------ | ------------------------------------------------------------------------------ |
| Round-wise final alignment     | 第 `r` 组倾向与最终政策判断相同的比例是多少？是否越接近末轮越高？              |
| Last-round alignment           | 最后一条 Judge OS（偶数总回合制为第 N-2 回合）与最终政策判断一致的比例是多少？ |
| Probability gap                | 同组内 `abs(p_os(g,r) - p_final(g))` 随回合如何变化？                          |
| Calibration / Brier score      | 重复 OS 样本形成的经验概率，是否能校准到最终变法频率？                         |
| Tendency volatility            | 每场轨迹平均改变倾向多少次？Context 方案是否只是在强行平滑结果？               |
| Fixed-input instability        | 完全相同输入重复生成时，tendency 分裂程度是多少？                              |
| Prompt-strength sensitivity    | prompt 由弱到强时，每轮 `p_os` 是否出现合理的方向性变化？                      |
| Latency / tokens / concurrency | Context 方案带来的墙钟时间、输入 token、成本和最大并发是多少？                 |

不能把 100% 一致当作唯一目标。当前最终裁判还可能看到赛后问询、隐藏请求和完整辩论，而 C0 Judge OS 只看两次发言。二者不一致可能来自新增证据或任务定义不同，不一定是模型自相矛盾。

建议同时保留两个最终标签：

- `F_full`：真实生产流程的最终政策判断，包含赛后问询等现有输入；
- `F_debate_only`（实验标签）：只基于完整辩论重新做一次政策判断，用于隔离赛后新增证据的影响。

## 7. 建议的实验执行顺序

### Phase 1：最小可行一致性实验

1. 从商鞅 Judge Sensitivity 数据中分层选取一小组完整历史，覆盖弱、中、强 prompt 和不同最终胜率区间；
2. 只测试同一 GLM-5.1 thinking 配置；
3. 对每段历史分别生成 C0 和 C4；
4. 每个回合/context 重复若干次，使 `p_os` 真正可估计；
5. 比较 round-wise alignment、last-round alignment、volatility、fixed-input instability、延迟和 token；
6. 预先登记样本、排除规则和指标，避免看到结果后挑选有利口径。

### Phase 2：Context 扩展

- 若 C4 的一致性明显优于 C0，再加入 C5 测试成本/记忆窗口；
- C1/C2/C3 只用于检验“自我记忆是否让轨迹更平滑”，并单独报告串行延迟和锚定风险；
- 固定 transcript，随机化不同 Context 方案的调用顺序，按完整请求 hash 缓存结果。

### Phase 3：跨模型与真实分布

- 在 Judge Bias 数据中，每个最终裁判模型只与同模型 Judge OS 比较；
- 用 Judge Sensitivity 数据比较 thinking on/off 和不同模型的轨迹稳定性；
- 最后才把方法用于真实用户对局，并将结果标注为探索性观察而非固定 prompt-pair 胜率。

## 8. 验收标准

### 基础功能

- 只在配置了 Judge OS 的指定场景启用；
- 除最终发言组外，每个完整 A/B 发言组恰好生成一条，不在奇数回合或最终偶数回合生成；
- 10 回合制只生成 OS_2/4/6/8；20 回合制只生成 OS_2/4/6……18；
- 输入符合所选 Context 方案，不发生最终标签或对手 prompt 泄漏；
- 模型、thinking 模式和人设版本满足配置要求；
- 输出严格符合 schema，`reason` 每轮存在；
- 辩论不等待 Judge OS；允许多个 OS 同时生成；
- 发言生成后立即持久化和展示，不因对应 OS 尚未完成而延迟；
- 乱序完成不会造成乱序展示或旧持久化快照覆盖新快照；失败占位也参与顺序发布；
- 恢复时不重复已持久化的连续成功或失败结果；
- OS 生成、解析或中间持久化失败不使整场对局失败；
- 赛后问询和最终裁判不等待 OS；计分后只做有界收尾；
- 宽屏 OS 框位于辩论框右侧，成功节点可展开原因；
- 每场保存实际 OS prompt 快照/hash、模型和请求配置；
- Judge OS 不进入最终裁决或程序化计分输入。

### 实验

- 每个结果可追溯到原始 history、transcript hash、prompt pair、模型/config 和 prompt hash；
- Judge OS 模型/config 与其对比的最终裁判完全匹配；
- 概率只从重复样本或明确定义的同质分组估计，并始终报告 `N`；
- `judgment` 与 `winner` 分开分析；
- 报告失败、重试、缺失结果和实际调用次数；
- 同时报告一致性、稳定性、延迟和成本，不只挑选单一有利指标。

## 9. 后续实验与非 v1 问题

以下问题不阻塞 v1 合入：

1. C4（截至当前的全部辩论）与 C5（最近 K 组）相比，哪一个更适合作为累计信念实验？
2. 是否应把 Judge OS 与普通 Judge 共用的人设抽成独立 `judgePersonaPrompt`，从根源上消除两个 prompt 的人工同步成本？v1 采用独立 prompt + 管理员复核 + 每场 provenance。
3. 是否需要为跨对局并发增加单独的 Judge OS provider 限流器？v1 保留每场完全并发并依赖现有调用 telemetry 观察容量。
4. 若未来实验置信度，采用模型自报、重复采样经验比例还是另建校准器？v1 不向玩家展示置信度。
5. 若未来存在玩家能在辩论中途改变输入的交互模式，是否需要关闭实时 OS？当前自主辩论保持实时展示。
