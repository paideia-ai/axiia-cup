## 2026-09-09 修订：咳嗦「低 → 高 → 低」三页层级

本修订采用咳嗦 2026-09-09
的三页方案，并作为这三页的最新验收依据：一级清单低信息、单体主页高信息、构建器低信息。这里的“取代”只针对页面信息架构、控件位置、文案和导航；未明确列出的
v3.4 条款继续有效。

### 一级：`/my-agents` 我的智能体（低信息）

- 按场景分组，每一侧只展示一次角色名与简短说明；其下每个智能体是一整行可点击链接，进入
  `/agents/:id`。
- 行内只保留身份和轻量参赛态提示；不展示版本数、最近编辑时间、模型等元数据，也不放重命名、删除、查看、编辑或出战按钮。参赛智能体可用克制的强调边框表示，但整行仍是唯一主入口。
- 每侧角色说明旁固定一个机器人加号的新建入口；空侧也使用相同入口。桌面为紧凑图标，移动端点击目标不得小于
  `44 × 44px`。
- 新建采用带可选名称的桌面锚定浮层 / 移动端底部
  sheet；创建成功先进入该智能体主页 `/agents/:id`，不直接进入构建器。
- 场景详情的“查看我的{角色}”保留上下文：该侧恰有一个智能体时直接进入其
  `/agents/:id` 主页；有多个时进入可刷新、可返回完整清单的
  `/my-agents?scenario=:scenarioID&side=a|b`
  聚焦视图。聚焦视图只展示指定场景和指定侧；无效或过期参数安全回落完整清单。
- 场景详情原有的两个“构建一个{角色}”主按钮按 2026-09-09
  最终决定原样保留；空侧可由此 ensure
  智能体并直接进入构建器。这是场景详情的明确快捷入口，不改变清单/主页机器人加号“创建后先到主页”的行为。
- 场景级双侧完成度、参赛就绪摘要与缺侧/未标记校验保留；同侧第二个智能体仍受对侧已有已保存版本的服务端门槛约束。

### 二级：`/agents/:id` 智能体主页（高信息）

- 主页是所有者管理单个智能体及其版本的中心：标题、重命名、仅限空智能体的删除、同角色智能体横向栏、版本内容、版本备注/模型/时间/战绩、复制、展开、参赛选择、真实出战和版本对比都集中在这里。
- 同角色栏即使只有一个智能体也始终出现，当前项有明确选中态，末尾固定机器人加号的新建入口。标题旁的更多菜单承载重命名与删除；已有版本的智能体不可删除。
- 版本标题旁用铅笔加号进入 `/agents/:id/build`
  创建新版本。版本卡采用紧凑操作：复制提示词、勾选为该侧参赛版本、以该版真实出战；仅正文实际超过三行时出现展开/收起。版本对比默认折叠，选择任意两版后自动刷新，不另设“对比”提交按钮。
- 主页不重复放双侧完成度提醒；双侧状态集中在一级清单和实际门槛处。非所有者的公开投影仍只展示允许公开的身份与逐版本战绩，不展示提示词、复制/参赛/出战控件或
  diff。

### 三级：`/agents/:id/build` 智能体构建器（低信息）

- 构建器只服务当前工作区：策略文本、实时字数、模型、可选角色
  persona、可选版本备注、当前草稿复制、自动暂存，以及可展开的只读官方角色系统提示词。
- “选择预设策略”和“让你的 AI
  帮你想策略”两个辅助入口在空草稿、非空草稿、首版前及已有版本后都始终可见，详细流程在可关闭对话框内完成；外部
  AI 流程只提供元提示词复制，不在产品内模拟聊天。
- 构建器不显示版本列表、参赛选择、版本对比或出战动作，也不提供“基于该版本迭代”。保存产生新的不可变线性版本后返回
  `/agents/:id`；普通保存不派发对局。首战 express
  的“保存并自动开战、直达实况”仍是唯一的保存后导航例外。
- 从主页进入时沿用服务端草稿；没有草稿选择时继承最新版本的模型。预设替换已有草稿必须确认，且绝不修改已保存版本。

### 明确取代的 v3.4 UI 细节

以下旧要求不再作为验收标准：#64 在 EA/构建器重复展示双侧徽章的位置要求；#75
页头“编辑”必须与“出战”相邻；#83 三种辅助方式仅限首稿且保存后消失；#88
构建器内嵌完整版本线、EA↔E 动作同构及保存停留构建器；#89
“基于该版本迭代”版本卡动作；P1a 在一级清单显示最近编辑时间并据此排序；P2/P8b
在一级清单放重命名/删除；P9 同侧只有一个智能体时隐藏横向栏；P12
保存按钮旁常驻“保存后将成为 v(N+1)”；B3/E11 要求每张版本卡恰有“展开全文 /
设为参赛版本 / 基于该版本迭代 / 出战”四个文字动作。#90
“不提供复制为新智能体”继续有效；常规新增仍通过清单或主页的机器人加号，另保留上一节明确列出的场景详情“构建一个{角色}”快捷入口。

### 保持不变的产品与后端约束

- per-side
  数据模型、多智能体能力、同侧新增门槛（对侧须有已保存版本）、每版模型快照、逐方实时配置的
  1000 单位上限，以及模型清单均保持服务端权威。
- 工作区草稿继续由服务端自动暂存；保存只追加不可变的线性版本，不建立父子分支。某侧第一次保存仅在该侧尚无参赛版本时自动占用参赛位；之后保存不得悄悄移动
  ★。每个场景每侧最多一个参赛版本，跨同侧智能体改标时旧 ★ 必须清除。
- 参赛需双侧各有参赛版本；PVE/PVP/hotseat/赛事门槛与配对继续由后端校验。前端必须显示服务端拒绝文案，不能仅靠客户端禁用模拟规则。
- 所有页面使用登录态和真实 API 数据；禁止以 localStorage、demo
  inventory、合成/负数 id 或静态模型样本替代生产数据。出战使用真实 `OsPanel`
  与派发 API，不得使用模拟战斗确认。
- 提示词与 diff
  仅所有者可见；公开智能体投影不得返回或渲染提示词。对手提示词不可见、逐版本公开战绩、真实版本
  id、场景/裁判隐私边界均不变。
- 参赛入口的双侧校验、我的智能体页的完成度/就绪态，以及 express
  首战例外继续有效。本修订没有放宽任何鉴权、CSRF、隐私、成本或对战配额规则。

## 1. 产品概述

**产品名称：** Axiia Cup（AA Cup）

**一句话：** 选手编写策略提示词，打造 AI
智能体，在人文学科场景中进行对抗性对话比赛。

**目标用户：** 中国初高中及大学生

**MVP 目标：** 端到端展示完整用户体验。前端必须展示完整流程，后端可以不完善。

---

## 2. 用户流程

```
注册（邮箱 + OTP + 设密码） → 登录（邮箱 + 密码）
→ 选择场景 → 为某一侧创建智能体并编写该侧策略提示词（对侧另建智能体；参赛需两侧齐备，见 #58/#59）
→ 选择模型 → 试炼场测试（PvP 自测 / PvE 练习）→ 提交 → 异步对战 → 查看排行榜
```

## 3. 场景系统

每个 **学科**（历史、法律、戏剧、谈判等）下包含一个或多个 **场景**。

### 场景定义

| 要素                | 说明                                                            |
| ------------------- | --------------------------------------------------------------- |
| 学科                | 历史、法律、戏剧、销售、哲学等                                  |
| 背景                | 背景材料、情境设定、约束条件                                    |

## 6. 裁判系统

### 核心设计（已确认 2026-03-30，更新 2026-07-17）

**裁判 = 场景角色人设 + 公开提示词 + 对话期内心 OS（指定场景） + 多轮赛后提问 +
统计收敛**

| 设计原则             | 说明                                                                                    |
| -------------------- | --------------------------------------------------------------------------------------- |
| **裁判 prompt 公开** | 所有选手可查看裁判 prompt。对称博弈下，双方都能优化，不破坏公平                         |
| **裁判有角色人设**   | 不是抽象的评分机器，而是场景中的角色（如商鞅场景的**秦孝公**）                          |
| **赛后提问评分**     | 对话结束后，裁判角色向双方各提若干问题，根据关键回答评分。提问轮数可配置（默认 3 轮）   |
| **统计稳定性**       | 单场 LLM 判定有方差，但大量对局后统计收敛。德州扑克模型：规则公开 + 大量对局 = 长期公平 |
| **版本迭代**         | 裁判 prompt 版本化管理，根据玩家反馈公开更新，类似竞技游戏平衡补丁                      |

### 商鞅场景：秦孝公内心 OS（2026-07-15，更新 2026-07-17）

- 除最后一组发言外，商鞅与甘龙每各完成一次发言后生成一条，即 10 回合制在第
  2、4、6、8 回合后生成，20 回合制在第 2、4、6……18
  回合后生成；最后一个偶数回合及奇数回合不生成。
- 每组发言完成后立即启动一个独立生成任务，不等待上一条 OS 完成；多条 OS
  可以与后续辩论及彼此并发生成，双方无需等待，也不会收到或看到 OS
  作为对话上下文。
- 辩论发言在模型返回后立即持久化并展示，不等待对应 OS；OS
  自己生成完成后再展示。并发任务允许乱序完成，但只按第
  2、4、6……回合的连续顺序持久化和展示，较后的 OS 不得越过较早的 OS
  或其失败占位。
- 每次模型输入只包含刚完成的两次发言，不包含更早辩论或上一次倾向。
- 使用场景配置的裁判模型；生产商鞅场景为 GLM-5.1，并继承生产秦孝公裁判 prompt
  的人设与初始立场。
- 严格 JSON 输出 `afterTurn`、`tendency`、`reason`。`tendency`
  只能是“商鞅”或“甘龙”；`reason` 每次都必须输出，不以倾向是否改变为条件。
- OS 是 best-effort
  展示功能：单条失败或最终收尾超时只记录为不可用，不得让对局失败。辩论结束后，赛后问询和最终裁判立即继续，不等待
  OS；计分完成后再对仍在运行的 OS 做有界收尾。
- 前端将紧凑、可展开原因的 OS
  倾向轨迹放在对话记录框正上方；本版本不额外加入“仅供展示/非最终裁决/非
  chain-of-thought”的短说明文案。
- 普通裁判 prompt 保持公开；OS prompt 仅由管理员维护，不在
  Playground「场景资料」或玩家侧场景详情页公开。OS
  仅用于展示，不进入最终裁决或计分输入。每场运行保存 OS prompt 快照及
  hash、模型、thinking 模式、temperature、JSON mode、Context 版本和回合配置。
- 详细产品语义、Context 备选方案和一致性实验计划见
  [judge-os-feature-spec.md](judge-os-feature-spec.md)。其中未标为当前决定的方案仍属实验，不自动改变本规范以上规则。

### 多 Agent 陪审团票决扩展（2026-08-13）

- 场景可以显式声明 `meta.adjudicationMode = 'jury-vote'`，由多名场内 NPC
  共同承担裁决角色，替代单一 Judge。未声明时仍采用既有的单一 Judge 模式。
- 陪审团场景的胜负必须由脚本按照公开门槛机械统计成员票数，不再追加单一 Judge
  的赛后问询，也不要求生成 `judge-aside` 内心 OS。
- 每名陪审员仍须基于场景材料独立调用模型形成票和简短理由；脚本必须发布逐票揭晓及统一的结构化
  `score` 事件，供回放、计分推导和审计使用。
- 首个采用这一模式的场景是 `legal-harbor-murder-jury`：两名固定立场玩家与九名
  NPC 组成十一人陪审团，六票形成裁决。

### 待探索：裁判系统扩展方向（非 MVP）

以下为 3/31 会议讨论和后续设计思考中提出的方向，尚未纳入 MVP：

- **赛后提问微框架**：提问类型可包括秘密猜测（"对方的隐藏信息是什么？"）、策略评估、知识验证等
- **部分标准公开、部分隐藏**：公开标准让选手优化；隐藏标准考察"揣测上意"能力
- **评分维度**（杨斐提出）：学科知识与角色真实性、历史知识深度、辩论质量与说服力、策略运用、随机真伪历史点识别
- **客观指标 vs 人设化评判（chain of thought）**：待定
- 详见 [hidden-info-design-discussion.md](hidden-info-design-discussion.md)

### 裁判流程

```
对话阶段（20 轮） ── 第 2、4、6……18 回合并行生成内心 OS；发言展示不等待 OS
    ↓
裁判角色（秦孝公）向 Agent A 提问（与尚未结束的 OS 并行）
    ↓
裁判角色（秦孝公）向 Agent B 提问（若干问题，含秘密猜测等）
    ↓
根据关键回答计分 → 判定胜负
```

### 系统偏差应对

LLM 裁判可能有系统性偏差（如偏好更长回复、偏好某种修辞风格）。应对方式：

- 公开 prompt → 玩家发现偏差并反馈
- 运营方更新裁判 prompt → 发布更新说明
- 这就是竞技游戏的标准平衡流程

## 7. 对战引擎

| 项目               | 规则                                                                                    |
| ------------------ | --------------------------------------------------------------------------------------- |
| 执行方式           | 全异步。对战在后台运行，选手后续查看结果                                                |
| 对话轮数           | 场景作者自定义（10-20 轮，默认 20）                                                     |
| Temperature        | 0（确定性输出）                                                                         |
| API 失败处理       | 从失败点重试（不重启整场对战）                                                          |
| 对手 prompt 可见性 | 不可见                                                                                  |
| 配对方式           | 每对选手打两场（#66 成对约战）：甲的 A 侧智能体 vs 乙的 B 侧，及 甲的 B 侧 vs 乙的 A 侧 |

### 对战生命周期（5 阶段）

每场对战（试炼场自测 / 正式比赛）经过以下阶段：

| 阶段        | 状态码             | 说明                                           |
| ----------- | ------------------ | ---------------------------------------------- |
| 1. 提交     | `submitted`        | 系统收到对战请求                               |
| 2. 排队     | `queued`           | 等待执行槽位                                   |
| 3. 对战     | `running`          | N 轮对话进行中，可查看当前回合（第 N/20 回合） |
| 4. 裁判评分 | `judging`          | 对话结束，裁判角色提问 + 评分中                |
| 5. 完成     | `scored` / `error` | 可查看完整对话记录和评分结果                   |

### 试炼场异步体验

试炼场是选手主动触发的自测（自己的角色 A vs 自己的角色 B）。因为 LLM 对话需要
2-5 分钟，采用异步模式：

- **提交后**：显示进度卡片（5 步骤条 + 当前对战 ID）
- **等待中**：文案提示"你可以离开此页面，稍后回来查看结果"
- **轮询**：「刷新状态」按钮手动检查进度（MVP）；进入页面时自动拉取最新状态
- **对战中**：实时显示"第 N/20 回合"
- **完成后**：可查看完整对话记录 + 裁判评分预览
- **失败时**：显示失败阶段 + 重试按钮

### 正式比赛（瑞士轮）的用户视角

瑞士轮由管理员触发，选手无需操作。选手视角仅为查看结果：

- **控制台**：显示近期对战列表，每条包含状态标签（胜出/落败/对战中）+ 相对时间
- **排行榜**：仅反映已完成对局的统计数据
- 选手无法主动发起正式对战，只能等待系统配对

### 状态标签配色

| 状态   | 颜色          | 用途       |
| ------ | ------------- | ---------- |
| 排队中 | 蓝色 `--info` | 试炼场等待 |
| 对战中 | 黄色 `--warn` | 对话进行中 |
| 胜出   | 绿色 `--ok`   | 完成且获胜 |
| 落败   | 红色 `--err`  | 完成且落败 |

## 8. 赛制

### MVP：单次瑞士轮

所有选手提交 prompt 后，管理员触发一次瑞士轮比赛。

### MVP 时间线（已确认 2026-03-31）

| 日期      | 事件                                                     |
| --------- | -------------------------------------------------------- |
| 4 月 7 日 | Info session：向参与者讲解规则和流程                     |
| 4 月 8 日 | 内部 MVP 测试开赛（15 人）                               |
| 5 月 1 日 | 正式比赛开赛（公开）                                     |
| 后续轮次  | 待定（初步讨论：5/23 提交 R1 → 6/15 提交 R2 → 8 月决赛） |

### 赛程结构（15 人示例）

```
赛前阶段
├── Info session：讲解规则、演示系统、Q&A
├── 注册 + 提交 prompt（时间窗口：10 分钟 ~ 1 小时）
├── 试炼场自测（hotseat 自打 #61 / PvE 练习）
└── 管理员确认参赛名单，触发比赛

比赛阶段
├── 瑞士轮 4 轮（自动配对 + 自动运行）
├── 预计总运行时间：3-5 小时（56 场顺序执行）
└── 公布最终排名
```

### 瑞士轮规则

- 每轮：战绩相近的选手配对（赢的打赢的，输的打输的）
- 配对算法：MVP 使用简单实现（按积分排序后相邻配对），具体由工程团队决定
- 不重复：同一轮赛中不重复配对
- 轮空：奇数人时 1 人轮空（算赢）
- 不淘汰：所有人打完全部轮次
- 每对打两场：系统为每个配对生成两条对战记录（A 的角色A vs B 的角色B，以及 A
  的角色B vs B 的角色A）

### 数字

| 参数         | 值                |
| ------------ | ----------------- |
| 参赛人数     | 15                |
| 瑞士轮数     | 4                 |
| 对战组数     | ~28               |
| 每组比赛场次 | 2（正反角色）     |
| 总场次       | ~56               |
| 每人对局数   | 4（×2 场 = 8 场） |

### 排名系统（MVP）

- **胜场数排序** + Buchholz 小分（对手平均强度）作为同胜场 tiebreaker
- 排行榜：排名、选手名、模型、胜率、场景

### 正式上线后扩展（非 MVP）

- **多轮瑞士制**：分 3 个 block，block 之间留迭代窗口，选手可改 prompt 再战
- **Elo/Glicko-2 rating**：跨 block 累计，实时更新排行榜
- **Prompt 迭代**：测量选手学习速度，不只是首版 prompt 质量

### 管理员操作

- 设定比赛开始时间（触发瑞士轮）
- 比赛开始后不接受新玩家

## 11. 竞品差异

**vs 狼人杀 AI 大赛：**

- 更简单（1v1 而非多人），token 成本低
- 强调人类设计者的能力，而非模型本身
- 人文学科方向，教育市场价值高

**vs OpenClaw / 工作流 Agent 大赛：**

- 它们测「agent 能做什么」（工具调用、自动化）
- 我们测「你能多好地设计对抗性对话策略」
- 完全不同的能力维度
