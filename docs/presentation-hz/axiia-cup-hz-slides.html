工程选择 1 / CLI

什么是 CLI

CLI 是 Command Line Interface，也就是命令行界面。在网页 UI 里用鼠标点按钮，在 CLI 里是在终端输入命令，让程序做事。

同一个后端操作

网页里可以点一个按钮：

Start Tournament

CLI 里则可能是：

axiia start shangyang-court
08

工程选择 1 / CLI

Web UI 和 CLI 的区别

一个网站完全可以只有 web app，没有 CLI。区别在于，CLI 提供了另一种 control surface。

适合谁

  • Web UI：适合人在浏览器里点。
  • CLI：适合人、脚本、CI、AI agent 在终端里操作。

适合什么操作

  • 编辑 scenario。
  • 开始 tournament。
  • 查看结果。
  • 导出数据。
09

工程选择 1 / CLI

为什么这对 Axiia Cup 有用

Axiia Cup 里有很多经常需要查看、修改和导出的东西。如果只能通过网页操作，很多迭代会比较慢。

经常需要操作的数据

  • scenario、player prompt、judge prompt、scorer prompt。
  • tournament、playground run、battle transcript。
  • LLM call logs。

为什么对 AI agent 友好

AI 擅长读文件、改 JSON、运行命令、看结构化输出，不需要像人一样在网页里一步步点击。

工程选择 2

Scenario data in database

Axiia Cup 预期会有多个场景，所以 scenario 不完全 hardcode 在代码里，而是存进数据库。

如果 hardcode

const scenario = {
  id: "shangyang-court",
  judgePrompt: "...",
  roleAName: "商鞅",
  roleBName: "甘龙"
}

为什么进数据库

  • 角色设定、judge prompt、scorer prompt 都会反复改。
  • 隐藏目标、对话轮数和新场景也需要测试。
  • 数据库让 scenario 更方便编辑、测试和迭代。
11

工程选择 3

Database schema

把 scenario 放进数据库之后，更难的问题是：schema 应该长什么样？也就是必须有哪些字段、每个字段是什么格式。

难点

  • 商鞅变法有隐藏请求和赛后问询。
  • 本能寺之变有可选角色。
  • 电车难题没有隐藏目标，更像多个伦理案件的逐案辩论。

太死 / 太松

schema 太死，只能支持一种场景；schema 太松，又很难验证、运行和调试。

工程选择 4

Langfuse

Axiia Cup 里，一场比赛不是一次 LLM 调用，而是一串连续调用。人的困难是：要知道模型到底看到了什么、说了什么、在哪一步出错。

一局比赛是一串调用

  • player agent A 发言。
  • player agent B 回应。
  • 继续多轮对话。
  • judge 阅读对话并裁决。
  • scorer 根据裁决和规则计算分数。

Langfuse 让什么可见

  • 这一轮是谁在发言、使用哪个模型。
  • 输入 prompt、模型返回、call 属于 player / judge / scorer。
  • 耗时、报错、token 使用量。

为什么重要

没有观察工具，只能看到赢了、输了、失败了；很难知道是 player 没遵守角色、judge prompt 上下文不对、scorer 没解析输出，还是模型返回了格式错误的 JSON。
