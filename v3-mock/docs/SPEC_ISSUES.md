# 实现 v3.3/v3.4 规格时发现的问题

> 按「实现时被迫做决定/无法实现/规格自相矛盾」的标准收录。
> 每条给出：问题、影响、mock 里的临时处理、建议。
> v3.4 per-side（#55–#64）新增问题见文末 P4。

## P1 — 会影响实现方向的问题

### 1. 首战「直接进实况」与「每日上限/入队拒绝」的交互未定义（#9 × #52）
- **问题**：#52 定义触顶行为是「拒绝入队」，但首战不入队（#9 直接实况）。新注册用户理论上不会触顶，但「赛事阻挡全部试炼」（#47）期间注册的新用户，其首战是否也被阻挡？阻挡时快速通道停在哪一步、给什么文案，规格没说。
- **影响**：express 流程的失败分支 UI 无从设计。
- **mock 处理**：首战同样会被 #47 开关阻挡，express 构建页显示 inline 提示。
- **建议**：规格明确「#47 阻挡是否包含首战快速通道」；若包含，W4 的 express UI 设计需补一个被阻挡态。

### 2. ~~「只写一方」的版本在后续正式流程中的地位不明（#8 × #33）~~ ✅ 已被 v3.4 取代
- **v3.4 解决（#55/#57/#58）**：agent 本就单侧，不存在「半满」版本；「版本完整性」问题消失。
  参赛门槛改为「每侧各标一个参赛版本」（#58），校验落点在锦标赛报名/参赛标记层（见 BACKEND_REQUIREMENTS C0-2'）。

### 3. PVE 对局是否消耗每日次数、是否也走「进行中的对战」条（A3 × A5）
- **问题**：#45 说「每日对战次数上限」（每玩家），A5 的入队文案都以 PVP 语境为主。PVE 练习是否计入同一上限？（若计入，门槛进阶「PVE 练两侧」会被上限卡住。）
- **mock 处理**：PVE 与 PVP 共用同一每日上限（按 #45 字面「对战次数」）。
- **建议**：明确上限口径（PVE+PVP 合计 or 分开计），因为它直接决定成本模型（#45 的来源就是成本上限）。

### 4. 「按汉字或英文词计」缺精确算法（#14）
- **问题**:「1000，按汉字或英文词计」没有定义混排、标点、数字、markdown、空白的计法。前后端必须逐字节一致，否则会出现「前端放行、后端拒绝」。
- **mock 处理**：CJK 字符各计 1 + 连续拉丁/数字串各计 1，标点空白不计（`countPromptUnits`，src/mock/config.ts）。
- **建议**：把计数算法（正则级别）写进规格或 W14 工程项，并给测试用例。

### 5. 裁判 OS ①「默认显示」在实况中的时序未定义（#22 × A7 实况）
- **问题**：裁判 OS 生成层「对话期间并行生成」（DESIGN_SPEC）且默认公开显示。实况观看时它是否实时逐条出现？若是，观战的对手玩家等于实时看到裁判倾向——这是有意的吗？（战报完成态公开没有争议；实况阶段的公开会影响还在进行的对局吗？由于双方都是 agent 不是人在操作，影响可能只是观感。）
- **mock 处理**：实况中裁判 OS 实时逐条显示（对所有观众）。
- **建议**：确认实况阶段裁判 OS 的可见时机（实时 vs 完成后），写入 A7。

### 6. 天梯未建时「自动匹配（计分）」tab 的行为完全未定义（A5 tab3 × W11）
- **问题**：A5 要求 OS 面板有「3 自动匹配（计分）」tab，但匹配算法、计分、防刷全部在 W11 待设计。alpha 若上线此 tab，点了会发生什么没有任何规格。
- **mock 处理**：tab 存在，mock 随机选同场景公开版本为对手，并标注「W11 待设计」。
- **建议**：要么 alpha 隐藏该 tab（但与 #18「未完成的控件完全隐藏」一致的话，tab 2「顶尖玩家」的排序依据也未定，W11 前两个 tab 都该藏？），要么给 W11 一个最小可用定义。**#18 与 A5 的 tab 清单存在潜在冲突**。

### 7. 「顶尖玩家」tab 排序依据未定（A5 tab2 × W11）
- **问题**：规格自己标注「天梯未建时『顶尖』按什么排 → W11 一并定」。tab 在 alpha 范围内，排序却待定。
- **mock 处理**：按近期锦标赛战绩排序，UI 标注为临时。
- **建议**：同上，W11 前需要临时排序的正式决定（锦标赛战绩 / 总胜场 / 注册顺序均可，但要定）。

## P2 — 规格内部不一致 / 表述问题

### 8. ~~EA 展示名「按场景」仍带问句标记（#36 后半 / B3）~~ ✅ 已被 v3.4 取代
- **v3.4 解决（#63）**：#36 展示名问题被 per-side 取代——agent 名天然含侧，展示为「侧角色名 + 场景」。
  精确格式仍待确认，见 P4 #29。

### 9. F（Battleground）中文名缺失（W15），但 FA 三态里「进行中·实况」页面事实上就是 F
- **问题**：A7 说「F＝战报+发起者的运行控制，不是独立页面」，但「运行控制」具体指什么（中止？重跑？）规格从未列举。
- **mock 处理**：未实现任何运行控制按钮（除回放/分享/debug）。
- **建议**：列举发起者可用的运行控制（若 alpha 无任何控制，删掉这句话以免误导实现）。

### 10. 通知⑦「参赛版本提醒（锁定前确认）」缺触发定义（#53/B5）
- **问题**：「锁定前」指锦标赛报名截止前？截止时间从哪来？规格无锦标赛报名/锁定流程。
- **mock 处理**：类型存在（种子数据未包含此类通知）。
- **建议**：W6/W11 之外补一个「锦标赛报名与版本锁定」的最小流程定义。

### 11. 「进行中的对战」条的保留时长/容量未定义（A1/A5）
- **问题**：「刚完成」的对局在条里留多久？条最多显示几张卡？
- **mock 处理**：显示全部排队+进行中 + 最近 3 场已完成。
- **建议**：给一个可配置旋钮（进 §C2）或明确「完成后 X 分钟消失」。

### 12. 统计门槛「按 agent 计」的口径歧义（#39）
- **问题**：「该场景发生了多少场 battle，按 agent 计」——一场对局有两个 agent，是计 1 还是计 2？「按 agent 计」也可读作「只数 agent 对局（排除 NPC？）」。
- **mock 处理**：按「每场对局计 1」处理，NPC 局包含在内。
- **建议**：给出精确定义（例如「该场景已完成对局总数，含 PVE」）。

### 13. 侧方胜率的数据来源与门槛关系未说明（#38 × #39/#54）
- **问题**：统计展示门槛管住了「统计」，但侧方胜率也是统计——未过门槛的新场景，GLANCE 层的侧方胜率显示什么？#54 空态轮廓是否覆盖侧方胜率？
- **mock 处理**：未过门槛时侧方胜率一并进入空态轮廓（不显示数字）。
- **建议**：明确 #38 的胜率是否受 #39 门槛约束（mock 假设：受约束）。

### 14. 「模型永远公开」与 NPC 的模型（#21 × #48）
- **问题**：PVE-NPC 的模型是否也公开？NPC 提示词属场景内容不公开（§C1），模型呢？
- **mock 处理**：NPC 模型照常公开显示。
- **建议**：一句话确认即可（大概率「公开」，与 #21 一致）。

### 15. debug mode 的作用域与入口未定义（A7）
- **问题**：「debug mode 本身任何观众可开」——是每战报独立开关、会话全局、还是 URL 参数？对回放是否生效？
- **mock 处理**：会话全局开关，战报页内切换，对回放同样生效。
- **建议**：定为战报页内开关即可，但写明作用域。

## P3 — 规格没错但值得注意

### 16. 反注入明确不设防（A3 沿 v3.2 EXP-2）
- 规格原文「我们不介意大家注入」。注意这会与「裁判 OS 必须存在」（#23）互动：注入若能让裁判模型输出畸形结构化数据（W7 schema），失败重试语义（W17）要能兜住。

### 17. 可见性依赖后端过滤
- mock 在 UI 层隐藏受限项（提示词/diff/己方 trace），真实系统必须在 API 层过滤（见 BACKEND_REQUIREMENTS §5），否则「查看源代码」即泄露。规格 W16（矩阵配置位置）应写明「过滤在服务端」。

### 18. 首页示范对局的「白名单」机制无规格（B1）
- 谁来标记白名单、按什么标准，未定义。mock 用固定 id。建议进 §C2 配置注册表。

### 19. D 列表的基础排序未定义（A4）
- 除「新场景固定第 2 位」（#54）外，其余场景按什么排（上线时间？热度？难度？）规格没说，「最热门」精选又被推迟（#37）。mock 按数据定义顺序。建议给默认排序规则。

### 20. NPC 的难度表达未定义（#28 × #40）
- 场景有难度三档（#40），NPC 只有「最容易」排序（#10 用）。NPC 卡上难度如何标（沿用三档？序号？）未说。mock 用「最容易」徽章 + 序号。

### 21. 回放「全部内容从 0 到终局」的范围（A7）
- 「全部内容」是否包括结果/计分推导/问询的重演？mock 只重演对话 + 裁判 OS（其余在回放期间暂隐，结束后恢复）——若要求连判决也动态揭示，教学节奏设计（W7 锚点）需要更多规格。

### 22. 「顶尖玩家」tab 是否限定当前场景（A5）
- OS 面板绑定某场景的 agent，但顶尖玩家可能成名于其他场景——能否跨场景挑战？（对局需要双方在同一场景。）mock 禁用跨场景挑战按钮并注明。建议 tab 只列同场景玩家。

### 23. 通知组内排序未定义（B5/#53）
- 「优先级：PVP/锦标赛 > PVE」定义了组间顺序，组内按时间还是按类型未说。mock 组内按时间倒序。

### 24. MCQ 版本的「二次编辑」语义未定义（A2/W1）
- 从 MCQ 版本继续编辑时，勾选状态如何恢复？版本只存拼装后的纯文本（产出统一为纯文本），deck 内容一旦改版，旧版本的勾选无法可靠反推。mock 按 fragment 文本匹配反推（有损）。建议：版本另存 MCQ 选择元数据（W1 schema 应包含）。

### 25. 「每日」的时区口径未定义（#45/#46/#52）
- 每日对战上限、PVP 每日限次的「日」按什么时区切换（用户本地 / 服务器 / UTC+8）未定义；跨时区用户会遇到「明天」提前或推迟到来。mock 按浏览器本地日期。建议规格定为 UTC+8（目标用户在国内）并写明。

### 26. 计分 PVP 完成时发哪种通知有重叠（#53 ①×③）
- ①「对局完成（你发起的 PVE/PVP 出结果）」字面上覆盖计分 PVP，③「自动匹配结果」也覆盖——同一事件命中两类。mock 选择：计分 PVP 只发 ③（含天梯变动），其余发 ①。建议规格明确二选一。

## P4 — v3.4 per-side（#55–#64）实现时新发现

### 27. #59 引导门「已建过」的时态未定义
- **问题**：「想建第 2 个商鞅 → 必须先**建过** ≥1 个甘龙」——是「曾经建过（含已删）」还是「现存」？0 个版本的空 agent 算不算「建过」？
- **mock 处理**：按「现存 agent」计；空 agent 也算。
- **建议**：规格定为「现存」，并明确删除 agent 后门是否重新闭合（同 D16 一起写进 #59）。

### 28. hotseat（#61）的配额与战绩口径未定义
- **问题**：自打是否计入每日对战上限（#45）与并发上限？两侧版本的胜负是否都写入逐版本战绩？会不会被刷战绩（两侧都是自己）？
- **mock 处理**：计入发起人每日上限与并发；两侧版本各记一笔胜/负；不计天梯、不算 NPC 门槛。
- **建议**：明确 hotseat 战绩是否与对外战绩分开展示（EA 公开视图里的逐版本胜负含不含自打）。

### 29. #63 展示名的精确格式待确认（规格自注）
- **问题**：「商鞅 X · 商鞅变法」里 X 是自起名还是编号？自起名放主标题还是副标题？（#63 括注「解读待确认」。）
- **mock 处理**：`侧角色名「自起名」· 场景名`，侧角色短名去括注。
- **建议**：Yihan 确认格式，同时定 D 卡片/OS 面板等紧凑处的短格式。

### 30. 对手无对侧 agent 时的约战/匹配行为未定义（#62）
- **问题**：约战必须选对手对侧的 agent-version——若对手在该场景只有与你同侧的 agent，按 id 约战永远失败；自动匹配同理（候选池按对侧过滤后可能为空）。「默认打对方最新版」也要改成「对方**对侧**的最新版」。
- **mock 处理**：同侧版本直接拒绝（`wrong-side` 错误 + 明确文案）；自动匹配候选为空时提示无对手。
- **建议**：规格明确失败文案与「按玩家约战」时的默认解析规则（对侧最新版）。

### 31. v3.4「无迁移」只对后端成立
- **问题**：规格说「规格向 v2 靠拢，无迁移」——但任何已按 v3.3 形态（两方一体）落库的数据（含本 mock 的 localStorage）都需要拆分或丢弃。
- **mock 处理**：换 localStorage key（v2→v3），旧演示存档直接丢弃。
- **建议**：若正式系统已有两方一体数据，补一行 C4 式「上线时对现有玩家发生什么」。
