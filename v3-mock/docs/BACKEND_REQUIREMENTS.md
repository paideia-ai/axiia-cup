# v3.3 前端明确需要的后端支持

> 这里列出 mock 前端里每一处「假装后端存在」的地方——真实实现时后端必须提供的能力。
> 按规格引用标注（#n / A5 / W7 等）。mock 内对应位置在 `src/mock/store.ts` / `src/mock/engine.ts`。

## 1. 配置下发（#44 / §C2）

规格要求一切配置走文件 + CLI、不做后台 UI，且**数值不写死前端**（#39 明确「阈值可配置、不写死前端」）。
→ 前端需要一个**只读配置接口**（如 `GET /v1/config`），下发至少：

- 统计展示门槛（对局数，按 agent 计）
- 每日对战次数上限 + 当前用户今日已用次数
- PVP 解锁门槛 N（赢过 N 个不同 NPC）
- 每场景 PVE-NPC 数量
- 新手预设三元组（场景 / 执方 / 对手 NPC）
- 模型清单（id + 展示名）
- 可见性矩阵（受限项清单；落点 W16 未定）
- PVP 每日限次、并发上限
- 难度三档 + 「适合新手」标注（逐场景，也可并入场景数据）

mock 对应：`src/mock/config.ts` 的 `CONFIG` 常量。

## 2. 场景数据（A4 / #42 / W2）

DA 页「计分规则从场景数据读取，不硬编码」（#42）、「精确权重全公开」（#26）。
→ 场景接口必须包含（W2 六字段已并入四层，#51）：

- 基本项：名称、学科、一句话、难度、适合新手、预计时长、上线时间（isNew 判定 #54）
- 双方角色卡：名称、公开要求、行动重点、**可选立场/请求项、开场白**（W2→EXPAND-1）
- 胜利条件（双方）、边界约束、背景故事
- **隐藏信息真假配置概况、赛后问询方式、对话轮数、阶段结构**（W2→EXPAND-2）
- 裁判人设、裁判 prompt + 摘要、**裁判/计分模型**（W2→DEEP）
- 计分维度：key/label/**精确权重**/kind（结构化 vs LLM 软判断）/说明
- 隐藏目标 how-to 文案
- MCQ deck（schema 属系统 W1：逐题喂方、单/多选、选项→提示词片段）
- **注意：judgeOsPrompt 不得下发**（#51 维持不公开，仅管理员维护）

统计附件（#38/#39/#54）：每场景总对局数（按 agent 计）、双方侧胜率。

## 3. 智能体与版本（§0 / #13 / #14 / #17 / #33 / #35）

- 每玩家每场景**多个 agent**；版本逐 agent；版本快照 = 双方提示词 + **所选模型**（#13）
- 保存版本 ≠ 派发（#17）；**唯一例外**：express 首战保存自动派发
- 逐方 1000 字校验：**按汉字或英文词计（非 token）**（#14）——后端需与前端同一计数算法（算法本身需要规格定义，见 SPEC_ISSUES #4）
- express 首战允许**只有一方提示词**的版本（#8）——另一方为空的版本必须合法入库；正式参赛仍需双方齐全 → 需要一个「版本完整性」校验语义
- 参赛版本显式标记（#33），可改；schema 迁移时默认回填最新（C4）
- 版本 id 可分享、可按 id 查询用于约战（#25）→ id 需全局唯一且可解析出 agent/场景
- 逐版本**按侧**胜负统计（#35/#36）——需要按 (versionId, side) 聚合的战绩
- 版本 diff 仅所有者（#20）

## 4. 对局派发与执行（A5 / A7 / #9 / #27 / #52）

- 对局队列：入队（排队）→ 进行中 → 完成；「进行中的对战」条需要**当前用户已发起对局**的列表接口 + 状态推送
- **首战特殊路径**（#9）：不入异步队列，直接开始并以流式（SSE/WS）推送实况轮次
- 实况：进行中对局的逐轮推送（对话轮 + 裁判 OS ①条目）
- ETA：派发响应需带预计完成时间（B5 I-1「ETA + 完成后通知你」）
- 每日上限（#45/#52）：**只计发起人**；触顶返回明确错误（前端按钮保持可点，靠后端拒绝入队 + 错误文案）
- 赛事运行期间可阻挡全部试炼（#47）：后端开关 + 明确错误码
- PVP 友谊赛（#29）：按版本 id 或玩家最新版发起；**对方被通知、无需同意、不能拒绝**→ 后端直接执行并向被挑战者发通知；**不消耗被挑战者每日次数**
- 自动匹配（计分）：W11 未设计——前端已按 tab 占位，需要匹配接口 + 计分/天梯写入
- 真人对战（#30/W6）在 alpha 范围——数据模型需要第二参与者，完整设计待 W6 评审

## 5. 战报数据（A7 / #20–#27）

FA 是唯一对局视图（#27），一份对局数据接口需包含：

- 元信息：场景、类型（赛事/PVP计分/PVP友谊/PVE）、状态三态、**双方版本 id**（#25）、**双方模型（永远公开 #21）**
- 完整对话轮次
- 结果：胜者、双方总分、**裁判散文理由**（与结果分列）
- **计分推导**（#26）：逐维度（label/权重/kind/双方分/该维度判断说明）——系统层始终支持结构化，LLM 软判断也要如实还原每一步
- 赛后问询全文
- 隐藏目标分配与达成判定（对局结束后公开）
- **裁判 OS ①生成层**（#22）：独立 prompt 生成（保留裁判人设与模型）、**默认显示、公开**；生成时同步输出**结构化倾向数据**（favor/strength/changed/attention——schema 见 W7 草案）；「必须存在，不是 best-effort」（#23）→ 失败需重试语义（W17）
- **裁判 OS ②trace 层**（#22 修订）：裁判模型**真实 thinking trace**，公开，debug mode 查看 → 需要 LLM 网关把 reasoning/thinking 内容存下来
- **己方 OS trace**：双方 agent 模型的真实 thinking trace，**仅所有者**可见（#20）→ 存储 + 按 viewer 身份过滤
- 可见性过滤必须在**后端**做（#20 受限三项：提示词/diff/己方 trace）——前端 mock 里是 UI 层过滤，真实系统不能把受限数据发给非所有者
- 回放（A7）不需要新接口——用上述数据即可，但**裁判倾向锚点**依赖 W7 结构化输出落库

## 6. 门槛与进阶（A6）

- 「玩家赢过某 NPC」**事实记录**（按 玩家×场景×NPC 去重）——门槛判定依据
- PVP 解锁状态 + 进度（beaten/needed）查询
- 天梯（W11 待设计）：按玩家×场景计分、初始空、仅真实 PVP/锦标赛结果驱动
- 锦标赛：选择器 + 按轮时间线数据（GT tab）；天梯高分 → 直邀资格（#32）的判定与通知

## 7. 通知（B5 / #43 / #53）

- **站内通知持久化**（离线保存）、未读数、已读/清除、分组查询
- 8 种通知类型（#53）全部由后端产生：对局完成、被挑战、自动匹配结果、锦标赛进程、锦标赛资格、门槛达成、参赛版本提醒、系统公告
- 深链目标（战报 id / G 页）随通知下发
- 实时性：铃铛未读数需要推送或轮询接口

## 8. 首页与公开数据（B1）

- 白名单示范对局列表（含完整战报数据、裁判 OS 公开）
- 顶尖玩家、总对战数等聚合统计
- 未登录可访问（与 #20 可见性一致：对局内容本就公开，受限三项除外）

## 9. 认证（B2）

- 邮箱 + 密码登录；注册邀请码校验 + 注册即自动登录（→ 快速通道）
- 首战状态（expressPending / firstBattleDone）需要后端记录——决定新用户登录后落点（A3）
